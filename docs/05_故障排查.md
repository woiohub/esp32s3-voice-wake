# 故障排查手册

> 记录于 v0.4.0：定位并修复「唤醒初始化阶段 panic → 无限重启」。

---

## 1. 现象

串口日志反复打印同一段启动流程，每次都在 `AFE_SR` 打印完 `wakenet_init: 1` 之后崩溃：

```
I (500) main: voice wake system boot (fw 0.2.0)
I (520) drv:i2s: i2s ready: rate=16000, bits=16, mono
I (520) app:voice: config: volume=60 host=172.17.253.195:8888
I (530) AFE_SR: AFE version: SR_V220727
W (530) SR_SYS: PSRAM freq should be not less than 80MHz
W (540) SR_SYS: Data cache recommends 64KB
W (540) SR_SYS: Data cache line recommends 64B
I (550) AFE_SR: Initial auido front-end, total channel: 2, mic num: 1, ref num: 1
I (560) AFE_SR: aec_init: 1, se_init: 1, vad_init: 1
I (560) AFE_SR: wakenet_init: 1

Guru Meditation Error: Core 0 panic'ed (LoadProhibited)
PC      : 0x4200fb77  afe_create_from_config  (esp_afe_sr.c:337)
EXCVADDR: 0x00000000
Backtrace: afe_create_from_config <- wakeword_init (wakeword.c:48)
```

复位类型固定为 `rst:0xc (RTC_SW_CPU_RST)`，即软件 panic 后芯片自行复位，形成重启循环。

---

## 2. 关键时序

| # | 阶段 | 日志特征 | 说明 |
|---|------|---------|------|
| 1 | bootloader | `Partition Table` 打印 model @0x1f0000 / 0x300000 | 分区表本身被正确加载 |
| 2 | I2S 初始化 | `drv:i2s: i2s ready` | 与崩溃无关，可排除 |
| 3 | esp-sr 资源检查 | `SR_SYS: PSRAM freq ...`、`Data cache ...` 三条警告 | **AFE 需要的资源不满足** |
| 4 | AFE 配置打印 | `aec_init/se_init/vad_init/wakenet_init: 1` | 配置项读取正常，**但没有任何 `MODEL_LOADER` 输出** |
| 5 | 创建 AFE | `afe_create_from_config` 内 `memcpy` 访问 0x0 | LoadProhibited |
| 6 | 复位 | `RTC_SW_CPU_RST` → 重新 boot | 无自定义 panic handler，默认重启 |

**第 4 步的“无 MODEL_LOADER 输出”是定案证据**：esp-sr 的模型加载器（TAG=`MODEL_LOADER`）
在成功初始化时会打印 `The storage free size is ... KB` / `Successfully load srmodels`。
日志里完全没有这一段，说明 `esp_srmodel_init()` 从未被调用。

---

## 3. 根本原因

### P0-1 未加载唤醒模型（直接原因）

esp-sr 在 **ESP32-S3 / P4** 上，WakeNet 的模型数据 **不编译进 `libwakenet.a`**，而是：

1. 构建期由 `model/movemodel.py` 把选中的模型打包成 `build/srmodels/srmodels.bin`；
2. `idf.py flash` 把该文件写入分区表中名为 `model` 的分区；
3. **运行期必须调用 `esp_srmodel_init("model")`**，把分区 mmap 成静态模型表
   （`static_srmodels`），之后 `esp_wn_handle_from_name()` 才能按名字取到模型。

旧代码直接 `cfg.wakenet_model_name = WAKENET_MODEL_NAME;` 就调用 `create_from_config()`，
跳过了第 3 步，于是库内模型表为 `NULL`，`afe_create_from_config()` 内部对空模型数据
做 `memcpy` → `EXCVADDR=0x0` 的 LoadProhibited。

> 类比：模型文件只是“摆在了硬盘上”，但没有“挂载”，所以按名字查不到。

### P0-2 model 分区小于模型包（隐性原因）

| 项 | 数值 |
|---|---|
| `build/srmodels/srmodels.bin` | 3 994 828 B ≈ 3.81 MB |
| 分区表中 `model` 分区 | 0x300000 = 3 MB |
| 其中 `mn6_cn`（MultiNet 中文命令词） | 3.6 MB |
| 其中 `wn9_xiaomeitongxue_tts`（唤醒模型） | 289 KB |

- 模型包比分区大 0.81 MB，`idf.py flash` 仍按 `flash_args` 的 `0x1f0000 srmodels/srmodels.bin`
  整段写入，**溢出覆盖了紧随其后的 `ota_0` 起始约 830 KB**；
- 同时 `esp_partition_mmap()` 只能映射 3 MB，超出部分读不到 → 即便调用 `esp_srmodel_init()`，
  排在后面的模型也会拿到无效数据。

MultiNet 是“本地命令词识别”，本项目未使用，因此正确做法是关闭它以把模型包压到 ~300 KB。

### P1 硬件资源未按 esp-sr 要求配置

| 项 | 实际 | esp-sr 要求 | 后果 |
|---|---|---|---|
| PSRAM | `CONFIG_SPIRAM is not set` | 必须开启（HIGH_PERF 模式） | AFE 大块缓冲分配失败/回落，AEC 效果差，甚至创建失败 |
| PSRAM 频率 | — | ≥ 80 MHz | `PSRAM freq should be not less than 80MHz` |
| Data cache | 32 KB | 64 KB | 推理变慢，`Data cache recommends 64KB` |
| Cache line | 32 B | 64 B | `Data cache line recommends 64B` |
| Flash 头声明 | 8 MB | 实际 16 MB | `Detected size(16384k) larger than ...(8192k)`，可用空间被低估 |

### P2 配置漂移

- `sdkconfig.defaults` 里写的是 `CONFIG_SR_WN_WN9_HILEXIN=y`，但已生成的 `sdkconfig` 里是
  `CONFIG_SR_WN_WN9_XIAOMEITONGXUE_TTS=y`。**`sdkconfig` 一旦存在就不会再套用
  `sdkconfig.defaults` 的新增项**，导致文档与实际固件不一致（实际唤醒词是“小美同学”）。

## 5. 操作步骤（分区表已变，必须整片重烧）

```bash
cd firmware
# 1) 让新的 sdkconfig.defaults 生效（旧的 sdkconfig 不会自动吸收新增项）
idf.py fullclean
rm -f sdkconfig            # Windows: del sdkconfig

# 2) 重新生成配置并目视核对 4 项：PSRAM / cache / flash size / 唤醒模型
idf.py reconfigure
idf.py menuconfig
#   Component config → ESP-SR → Wake word: 至少勾选一个
#   Serial flasher config → Flash size: 16 MB
#   Component config → ESP PSRAM → 开启，Octal，80MHz
#   Component config → ESP System → Data cache 64KB / Cache line 64B

# 3) 构建，确认模型包体积小于 4MB
idf.py build
ls -l build/srmodels/srmodels.bin

# 4) 擦除后整片烧录（必须用 flash，不能用 app-flash，否则 model 分区还是空的）
idf.py -p COMx erase-flash
idf.py -p COMx flash monitor
```

### 验证要点

1. 启动日志出现 `model partition "model": N model(s)`；
2. `afe ready: model=... feed=512 ch=2`；
3. 没有 `Guru Meditation`，没有重复启动；
4. 说唤醒词，串口出现唤醒事件（`app:voice: wake detected` 等）。

## 6. 常见问题速查

| 现象 | 原因 | 处理 |
|---|---|---|
| 日志无 `MODEL_LOADER`，直接 panic 在 `afe_create_from_config` | 没调用 `esp_srmodel_init`，或 model 分区没烧 | 用 `idf.py flash` 整片烧录；确认 `wakeword_init` 先 init 再 create |
| `model partition "model" 里没有可用模型` | 分区被 app-flash 跳过 / 擦除过 | 重新 `idf.py flash` |
| `指定模型 "wn9_hilexin" 不存在，回退为 ...` | menuconfig 里勾选的模型和 Kconfig 名字不一致 | 改成一致的模型名，或直接删掉 `VW_SR_WAKENET_NAME` 让其回退 |
| `PSRAM freq should be not less than 80MHz` | PSRAM 未开或 40 MHz | 开 `CONFIG_SPIRAM` + `SPIRAM_SPEED_80M` |
| `Data cache recommends 64KB` | data cache 只有 32 KB | `ESP32S3_DATA_CACHE_64KB` + `DATA_CACHE_LINE_64B` |
| 启动即 `PSRAM ID read error` / 立刻重启 | 板子其实是 Quad PSRAM，却配了 Octal | 改 `SPIRAM_MODE_QUAD`（N8R2 类板子） |
| 反复重启但无 Backtrace（Brownout） | 供电不足（MAX98357 满功率 3.2 W） | 功放独立 5 V 供电、加大电容、共地 |
| `Detected size(16384k) larger than ...(8192k)` | flash size 仍为 8 MB | 改 `CONFIG_ESPTOOLPY_FLASHSIZE_16MB` |

## 7. 第二轮：`AFE_FEED` 持续报错与 I2S 时钟/格式核对（v0.4.1）

### 7.1 现象

模型加载与 AFE 创建都正常了，但每帧都打印：

```
E (1315) srv:wake: [0x2002:AFE_FEED] afe feed failed
```

间隔 10–30 ms，与 20 ms 音频帧节奏一致，但唤醒、WiFi、网络都照常工作。

### 7.2 结论：这是**误报**，不是 AFE 真失败

`esp_afe_sr_iface_op_feed_t` 的返回语义见头文件：

```c
/**
 * @param in  ... The frame size can be queried by the `get_feed_chunksize`.
 * @return    The size of input
 */
typedef int (*esp_afe_sr_iface_op_feed_t)(esp_afe_sr_data_t *afe, const int16_t* in);
```

返回值是「写入的输入长度」（正值），**不是 errno**。旧代码写成 `if (feed(...) != 0)` 判错，
于是每帧必然命中。已改为 `if (ret < 0)`，并首次打印返回值便于现场确认：

```
I (xxxx) srv:wake: afe feed ok: ret=1024 (feed_chunk=512, ch=2)
```

### 7.3 顺带修正：I2S 采样时钟与帧格式

对照 INMP441 手册（DS-INMP441-00 Rev1.1）：

> There must be **64 SCK cycles in each WS stereo frame**, or 32 SCK cycles per data-word.
> The INMP441 must always have 64 clock cycles for every stereo data-word (**fSCK = 64 × fWS**).

而 ESP-IDF 新版 I2S 驱动的 BCLK 计算为 `bclk = fS × total_slot(恒为 2) × slot_bit_width`：

| RX 配置 | BCLK @16 kHz | 是否满足 INMP441 |
|---|---|---|
| 16 bit 槽宽 | 32 × fS = 512 kHz | ✗ 只有要求的一半，帧不同步 → 噪声/静音 |
| **32 bit 槽宽** | **64 × fS = 1.024 MHz** | ✓ |

因此 RX 改为 **32bit 槽宽 + 单声道 + slot_mask(左/右)**，读到 32bit 后右移 16 位取高 16bit
（24bit 有效数据在 32bit 槽内左对齐、占用高 24 位）。

TX 侧 MAX98357A 需要标准两声道帧（LRC = fS，BCLK = 32×fS @16bit），
原实现用单声道 16bit 发送，右槽无数据，SD_MODE 若接成 (L+R)/2 会导致幅度减半甚至无声。
现改为 **16bit 立体声 + 单声道样本复制到 L/R 两槽**，兼容任意 SD_MODE 接法。

### 7.4 通道数核对（与 AFE 对齐）

| 层 | 通道数 | 说明 |
|---|---|---|
| INMP441 物理 | 1（单声道，L/R 决定落在哪个槽） | 只用左槽或右槽之一 |
| `audio_i2s_read` | 1 | 32bit→16bit，单声道 |
| `wakeword_feed` 输入 | 2（`[mic, ref]` 交错） | ref = 正在播放的 PCM，空闲时全 0 |
| `pcm_config` | `total_ch_num=2, mic_num=1, ref_num=1` | 与 `get_total_channel_num()` 一致 |
| WakeNet 检测模式 | `DET_MODE_2CH_90`（S3 默认，mode:2） | AEC 输出 + 参考，用于播报中打断 |

日志自检三行：

```
srv:wake: afe ready: model=... feed=512 ch=2          ← chunk/通道数
AFE_SR: Initial auido front-end, total channel: 2, mic num: 1, ref num: 1
MC Quantized wakenet9: ..., mode:2                    ← 2CH 检测模式
```

三者一致即说明通道数与数据格式对齐。

### 7.5 麦克风侧硬件核对清单

| 项 | 要求 | 自查方式 |
|---|---|---|
| L/R 脚 | 接地 → 左声道；接 VDD → 右声道 | 与 `menuconfig → INMP441 L/R 声道` 一致 |
| 供电 | 3.3 V（1.62–3.63 V），1.4 mA | 万用表量 VDD |
| SCK/WS | 由 ESP32 主控输出，fSCK = 64×fWS | 示波器量 BCLK 应为 1.024 MHz @16 kHz |
| SD 下拉 | 建议 100 kΩ 下拉，避免三态悬空 | 检查板上有无 |
| 数据有效性 | 说话时 `audio_i2s_read` 输出应有明显起伏 | 可临时打印 min/max 观察 |

> 若唤醒始终不触发，先确认麦克风数据是否真的有声音（而不是静音），再怀疑唤醒词/阈值。

## 8. 正常运行判读基线（v0.4.2）

### 8.1 一次健康启动应包含的日志

| 顺序 | 日志 | 含义 |
|---|---|---|
| 1 | `esp_psram: Found 8MB PSRAM device` / `Speed: 80MHz` | PSRAM 正常，AFE 有内存可用 |
| 2 | `drv:i2s: i2s ready: ... mic=32bit slot/mono(left) BCLK=1024000Hz` | **INMP441 时钟符合 64×fs** |
| 3 | `MODEL_LOADER: Successfully load srmodels` | 模型分区已烧录并 mmap 成功 |
| 4 | `srv:wake: model partition "model": N model(s)` | 模型表已注册 |
| 5 | `srv:wake: afe ready: model=... feed=512 ch=2` | AFE 创建成功，通道数 2 = mic+ref |
| 6 | `srv:wake: afe feed ok: ret=1024` | 首帧喂入成功（仅打印一次，后续不再刷） |
| 7 | `comm:wifi: STA 已连接 IP=...` | 已拿到 IP |
| 8 | `comm:net: connected to <host>:<port>` | **TCP 已连上上位机**（业务闭环的前提） |
| 9 | `app:voice: mic peak=...` | 麦克风通路有声音（说话时出现） |
| 10 | `app:voice: wake word detected` → `session N start` | 唤醒命中并开会话 |

**判断标准：1–7 出现 = 系统启动与音频链路正常；8–10 出现 = 业务闭环可用。**

### 8.2 常见“看起来正常但其实没跑通”的三种状态

| 现象 | 含义 | 处理 |
|---|---|---|
| 有 1–7，没有 8，且日志安静 | 上位机没启动/端口没监听/IP 不对，设备在静默重试（v0.4.2 起会打印 `连接 x.x.x.x:8888 失败(Connection refused, errno=111)`） | 先在上位机跑 `python main.py`，确认监听 0.0.0.0:8888；核对 `host.set` 的 IP |
| 有 8，说话但无 9 | 麦克风无声：L/R 接法、供电、SCK 时钟、SD 未接 | 按 7.5 清单核对；示波器量 SCK 应为 1.024 MHz |
| 有 9，无 10 | 唤醒词不匹配或阈值不合适 | 确认当前模型名字（日志第 4 行），说对应的唤醒词，如模型是 `wn9_xiaomeitongxue_tts` 就说「小美同学」 |

### 8.3 关于 `wifi:[ADDBA]RX DELBA, reason:1`

802.11 块确认（Block Ack）会话被对端拆除，`reason:1` 为 unspecified。
默认 `WIFI_PS_MIN_MODEM` 下设备周期性休眠，AP 会反复重建/拆除 BA 会话，属**正常现象**，
不影响功能，但会给音频链路带来 20–100ms 抖动。v0.4.2 起在拿到 IP 后执行
`esp_wifi_set_ps(WIFI_PS_NONE)`，这类日志会显著减少，同时降低上行音频时延。

## 9. 上位机启动失败排查（v0.4.3）

### 9.1 `NameError: name 'asyncio' is not defined`

```
File "voice_assistant\gui\main_window.py", line 153, in run_gui
    loop = asyncio.new_event_loop()
NameError: name 'asyncio' is not defined
```

**根因**：`run_gui()` 里用 `asyncio.new_event_loop()` 起后台事件循环，但模块顶部只
`import logging`，漏了 `import asyncio`（`py_compile` 只查语法，查不出这类名字错误）。

**修复**：顶部补 `import asyncio` / `import threading`，并去掉函数内的局部 `import asyncio as _aio`。

> 经验：这类错误用 **pyflakes** 静态扫描一次最省事：
> `python -m pyflakes main.py voice_assistant/*.py voice_assistant/gui/*.py`
> 本项目已跑过，当前 0 warning。

### 9.2 防火墙：设备连不上上位机（Windows 高频坑）

实测本机网络情况：

| 项 | 实测值 |
|---|---|
| 上位机 IP | `172.17.253.195`（WLAN 2） |
| 网络位置类别 | **Public（公用网络）** |
| 监听端口 | 8888（绑定 `0.0.0.0`） |
| `D:\anaconda\envs\voice-upper\python.exe` 的入站规则 | **不存在** |

Windows 在公用网络下默认拦截入站连接。即使 `python main.py` 正常监听，设备发起的 TCP 连接
也会被丢弃：设备侧打印 `连接 172.17.253.195:8888 失败`，上位机侧却看不到任何连接记录。

放行方式（管理员权限 PowerShell，二选一）：

```powershell
# 方式 A：按端口放行（换 Python 环境也不用改）
New-NetFirewallRule -DisplayName "VoiceAssistant TCP 8888" -Direction Inbound -Protocol TCP -LocalPort 8888 -Action Allow -Profile Public

# 方式 B：按程序放行
New-NetFirewallRule -DisplayName "VoiceAssistant python" -Direction Inbound -Program "D:\anaconda\envs\voice-upper\python.exe" -Action Allow -Profile Public
```

也可把该 WLAN 的网络位置改成「专用网络」：设置 → 网络和 Internet → WLAN → 属性 → 网络配置文件。

### 9.3 其他上位机侧检查项

| 检查 | 命令 / 现象 | 说明 |
|---|---|---|
| 端口是否真的在监听 | `Get-NetTCPConnection -LocalPort 8888 -State Listen` | 无输出 = 没监听成功（端口占用/绑定失败） |
| 端口是否被占用 | 启动日志 `TCP 监听 0.0.0.0:8888 失败` | v0.4.3 起会打印该错误并保留窗口 |
| 本机 IP 是否与下位机一致 | 启动日志 `本机 IP=...`（v0.4.3 新增） | 下位机 `host.ip` 必须是这个地址 |
| 从别的机器能否连通 | `Test-NetConnection 172.17.253.195 -Port 8888` | 失败多为防火墙，见 9.2 |
| LLM 是否可用 | 首次会话无回复、日志报 401 | `config.json` 的 `api_key` 未填 |

### 9.4 上位机启动成功的判定

```
INFO 上位机启动：监听 0.0.0.0:8888，STT=tiny(cpu)，LLM=glm/glm-4-flash，TTS=zh_CN-huayan-medium.onnx
INFO 本机 IP=172.17.253.195，下位机 host.ip 应填这个地址（当前配置 host_ip=172.17.253.195）
INFO tcp server listening on 0.0.0.0:8888
```

## 10. 反复连接/断开（周期约 2 秒）（v0.4.4）

### 10.1 现象

上位机：

```
device connected: ('172.17.253.46', 60948)
设备上线: {"device": "esp32s3", ...}
device disconnected: ('172.17.253.46', 60948)     ← 正好 2.0 秒后
device connected: ('172.17.253.46', 60949)        ← 1 秒后重连
...
```

下位机：

```
I comm:net: connected to 172.17.253.195:8888
I app:voice: host connected
W comm:net: recv closed (-1)          ← 2.0 秒后
I app:voice: host disconnected
```

### 10.2 根因 1（主因）：把 recv 超时当成断线

`socket` 设置了 `SO_RCVTIMEO = 2s`。没数据时 `recv()` 返回 `-1`、`errno = EAGAIN(11)`，
旧代码判断 `if (n <= 0) break;` —— 把「暂时没收到」当成了「对端关闭」，于是空闲链路
**每 2 秒被自己断开一次**，与日志中 2010 ms 的间隔完全吻合。

修复（`components/vw_comm/net_client.c`）：

```c
if (n > 0) { last_recv = now; feed(parser); continue; }
if (n < 0) {
    if (errno == EAGAIN || errno == EWOULDBLOCK || errno == EINTR) continue;  // 超时≠断线
    break;                                                                    // 真错误才断
}
break;                                                                        // n==0 对端关闭
```

### 10.3 根因 2：存活判定只看“收”，而上位机不回心跳

`client_task` 用 `now_ms() - last_recv_ms > 12s` 判超时。但上位机只在下行时才发包，
从不回应设备心跳 —— 即使修掉根因 1，第 12 秒仍会被判“心跳超时”再断一次。

两侧都改：

| 侧 | 修改 |
|---|---|
| 下位机 | 新增 `last_tx_ms`，`send_frame()` 成功即刷新；存活判定改用 `max(last_recv, last_tx)` |
| 上位机 | `pipeline.on_frame` 收到 `TYPE_HEARTBEAT` 回一帧心跳（`_reply_heartbeat`），让链路双向都有流量 |

### 10.4 根因 3（顺带发现，潜在致命）：上位机时间戳溢出

`protocol.now_ms()` 返回 Unix 纪元毫秒（约 `1.76e12`），而帧头 `ts` 字段是
`struct.pack(">I")`（上限 `4.29e9`）→ **上位机每发一帧就抛 `struct.error`**：

```
struct.error: 'I' format requires 0 <= number <= 4294967295
```

之前没暴露，是因为上位机从未主动发过帧（配置下发没人点、心跳没人回）。
一旦回心跳或下发音量，整条下发链路直接崩。

修复（`voice_assistant/protocol.py`）：

- `now_ms()` 改为 **自进程启动的毫秒**（`time.monotonic()` 差值），与固件
  `esp_timer_get_time()/1000` 语义一致，49.7 天内不会溢出；
- `build_frame()` 对 `seq`/`ts` 做 `& 0xFFFFFFFF` 掩码，越界不再抛异常。

### 10.5 验证

本地回环测试（真实 socket，不是 mock）：

```
HEARTBEAT REPLY TYPES: [4]     ← 下位机发心跳，上位机回了 TYPE_HEARTBEAT(0x04)
TEST DONE
```

板上验证：连接后应只剩一条 `connected to ...`，之后每 3 秒一次心跳，
**不再出现 `recv closed (-1)` / `host disconnected`**。

> 注意：本轮下位机也有改动，必须重新 `idf.py flash` 才会生效；
> 上位机是 Python，改完直接重启 `python main.py` 即可。

## 11. 麦克风有电平但唤醒不触发（数值恒为 ±21845）（v0.4.5）

### 11.1 现象

```
app:voice: mic peak=10922 (state=0)
app:voice: mic peak=24064
app:voice: mic peak=22528
app:voice: mic peak=21846     ← 反复出现
app:voice: mic peak=32768
app:voice: mic peak=21845
```

连接正常（`host connected`），但说唤醒词始终没有 `wake word detected`。

### 11.2 数值解码：这不是声音，是时钟串扰

把峰值换成十六进制：

| 十进制 | 十六进制 | 含义 |
|---|---|---|
| 21845 | `0x5555` | `0101 0101 0101 0101` |
| 21846 | `0x5556` | 同上 +1 bit |
| 10922 | `0x2AAA` | `0x5555` 右移一位 |
| 5461 | `0x1555` | 再右移一位 |
| 32768 | `0x8000` | 满量程负向（相位滑动） |

**全是 0101/1010 图案的家族**，且连续 40 秒每帧峰值几乎不变。
真实麦克风在安静房间的峰值是十几到几百、说话时几百到几千，且**帧帧变化**，
不可能长期稳定在 `0x5555` 这类常量上。

结论：ESP32 读到的不是麦克风的数据，而是**悬空的数据线拾取了 BCLK 时钟**。

### 11.3 机理

INMP441 只在属于自己的那个 I2S 半帧驱动 SD 线，其余时间**三态（高阻）**：

```
WS  ─┐     ┌─────┐     ┌──
      └─────┘     └─────┘
左槽: [ 24bit 数据 ]  [ 三态 ]   ← L/R 接地时只有左槽有数据
右槽: [ 三态 ]        [ 24bit 数据 ]  ← L/R 接 VDD 时反过来
```

- 读**对**的槽 → 正常数据；
- 读**错**的槽（或 SD 根本没接/没供电/CHIPEN 没拉高）→ 三态线在有 100kΩ 下拉时接近 0，
  但板上 BCLK 走线就在旁边，1.024 MHz 的时钟会耦合进来 →
  采到 `0101…` 图案 → 正是 `0x5555/0xAAAA` 家族。

AFE 收到的是纯噪声，自然永远不会唤醒。

### 11.4 修复：上电自动认声道（v0.4.6 改进版）

`components/vw_audio/audio_i2s.c`（`menuconfig → INMP441 L/R 声道 → 自动检测`，默认开启）：

1. **两个槽都测**（left / right 各采一段），启动日志并排打印，便于直接对比；
2. 每段采样前先 `vTaskDelay(60ms)` 并**丢弃第一块**——`i2s_channel_enable()` 后 DMA
   里是全 0，直接读会得到 `rms=0`，被误判成“安静的正常数据”（v0.4.5 就栽在这里，
   实测日志只有一条 `声道自检: rms=0 alt_ratio=0.00`，根本没换槽）；
3. 每个槽给出两个判据：
   - `has_data`：RMS ≥ 2（真实麦克风静音也有本底噪声，正好 0 说明没数据）；
   - `clean`：不是“等幅反号”的时钟串扰（`alt_ratio > 0.8 且 rms > 4000`）；
4. 选第一个 `clean` 的槽；两槽都不 clean → 明确报错并列出硬件清单；
5. 日志额外打印 `raw=xxxx xxxx xxxx xxxx`（前 4 个样本的十六进制），
   一眼就能看出是 `5555/AAAA`（串扰）、`0000`（无数据）还是真实音频。

也可以手动锁定：`menuconfig → INMP441 L/R 声道 → 强制左/右声道`。

### 11.5 修复后的预期日志

```
I (xxx) drv:i2s: i2s ready: rate=16000, mic=32bit slot/mono(left) BCLK=1024000Hz, amp=16bit/stereo
I (xxx) drv:i2s: 声道自检: rms=21845 alt_ratio=0.99        ← 当前槽是串扰
I (xxx) drv:i2s: 声道自检: rms=37 alt_ratio=0.02           ← 换槽后正常
W (xxx) drv:i2s: 当前声道数据像串扰，已自动切换到 right 声道
...
I (xxx) app:voice: mic peak=420 (state=0)                  ← 安静房间，数值正常
I (xxx) app:voice: mic peak=3860 (state=0)                 ← 说话
I (xxx) app:voice: wake word detected
```

若看到 `左右声道都像悬空/串扰`，说明问题在硬件侧，按 11.6 逐项查。

### 11.6 硬件复核清单（自动检测仍失败时）

先看最容易被忽略的一项：**CHIPEN（第 8 脚）必须接 VDD**。手册原文：
"When set low (ground), the microphone is disabled and put in power-down mode."
CHIPEN 悬空或接地 → 麦克风直接断电 → SD 全程三态 → 读到的就是 BCLK 串扰，
和“读错槽”表现完全一样。很多散装 INMP441 模块把 CHIPEN 悬空，这是首要嫌疑。

| 项 | 要求 | 说明 |
|---|---|---|
| CHIPEN（8 脚） | **接 VDD（3.3 V）** | 低电平=断电；悬空行为不确定，**必须**明确拉高 |
| VDD（7 脚） | 3.3 V（1.62–3.63 V），对 GND 加 0.1 µF | 供电不足会完全无输出 |
| GND（5/6/9 脚） | 与 ESP32 共地 | 不共地时数据全是垃圾 |
| SCK（1 脚） | 1.024 MHz @16 kHz | 示波器量；512 kHz 说明还是 16bit 槽宽（旧固件） |
| WS（3 脚） | 16 kHz，占空比 50% | 与 SCK 同源 |
| SD（2 脚） | 接 ESP32 的 DIN 脚，建议 100 kΩ 下拉 | 手册要求下拉，避免三态悬空拾取噪声 |
| L/R（4 脚） | 接地=左声道，接 VDD=右声道 | 悬空时行为不确定，必须明确接 |

## 12. 现场接线核对（INMP441 + MAX98357A + ESP32-S3-CAM）

### 12.1 逐线评审

**INMP441**

| 引脚 | 实际接法 | 结论 |
|---|---|---|
| VDD | 3.3 V | ✅ 在 1.62–3.63 V 范围内 |
| GND | GND | ✅ |
| SCK | GPIO5 | ✅ 与 `CONFIG_VW_MIC_BCLK_GPIO=5` 一致 |
| WS | GPIO4 | ✅ 与 `CONFIG_VW_MIC_WS_GPIO=4` 一致 |
| SD | GPIO6 | ✅ 与 `CONFIG_VW_MIC_DIN_GPIO=6` 一致 |
| L/R | GND | ✅ 左声道，与固件 `mono(left)` 一致 |
| **CHIPEN（第 8 脚）** | **未提及** | ⚠️ **首要嫌疑**：低电平/悬空 = 麦克风断电，SD 全程三态 |
| SD 下拉电阻 | 未提及 | ⚠️ 手册要求 100 kΩ 下拉到 GND，否则三态时容易被 BCLK 串扰 |

**MAX98357A**

| 引脚 | 实际接法 | 结论 |
|---|---|---|
| VIN | “按模块要求供电” | ⚠️ 需明确：2.5–5.5 V。**建议接 5 V**，3.3 V 时 8 Ω 负载只有约 0.4 W，声音偏小 |
| GND | GND | ✅ |
| BCLK | GPIO16 | ✅ 与 `CONFIG_VW_AMP_BCLK_GPIO=16` 一致 |
| LRC | GPIO15 | ✅ 与 `CONFIG_VW_AMP_LRC_GPIO=15` 一致 |
| DIN | GPIO7 | ✅ 与 `CONFIG_VW_AMP_DOUT_GPIO=7` 一致 |
| GAIN | GND | ✅ 按手册比较器门限 `0–0.1×VDD` → **12 dB**，音量足够 |
| SD_MODE | 3.3 V | ✅ 非 0 V 即退出 shutdown；固件把单声道复制到 L/R 两槽，左/右/(L+R)/2 任一模式都能出声 |

### 12.2 两个必须核实的地方

**① CHIPEN 到底有没有接高？**

INMP441 手册 Table 6：

> Pin 8 **CHIPEN**: Microphone Enable. When set low (ground), the microphone is disabled
> and put in power-down mode. When set high (VDD), the microphone is enabled.

- 若模块只引出 6 个焊盘（VDD/GND/SCK/WS/SD/L-R），通常板上已把 CHIPEN 拉高 → 无需处理；
- 若模块有 7 个焊盘或单独标了 `CHIPEN`/`EN` → **必须接 3.3 V**。

CHIPEN 为低时，SD 全程高阻，读到的正是 `0x5555` 这类时钟串扰 —— 和你日志里的
`mic peak=21845` 完全吻合。

**② ESP32-S3-CAM 的 GPIO4/5/6/7/15/16 是否被摄像头占用？**

常见 ESP32-S3-CAM（OV2640/OV3660 排线）的 DVP 引脚分布是：
`XCLK=15、SIOD=4、SIOC=5、VSYNC=6、HREF=7、D7=16` —— 与本项目 I2S 用到的引脚**完全重叠**。

- 摄像头**排线不要插**（只拔排线即可，转接座留着无妨）；
- 若排线插着，传感器会向 GPIO6(VSYNC)/GPIO7(HREF)/GPIO16(D7) 输出信号，
  与 I2S 直接打架，麦克风和功放都不会正常；
- 若必须用摄像头，需要重新分配 I2S 引脚（`menuconfig → Voice Wake System` 里改）。

### 12.3 建议的排查顺序（5 分钟）

1. 拔掉摄像头排线；
2. 给 CHIPEN（若有该脚）接 3.3 V；
3. SD 与 GND 之间加 100 kΩ 下拉（没有电阻可先跳过，看第 4 步结果）；
4. 重新烧录，看启动日志两行 `声道自检[left]/[right]`：
   - `raw=5555 5555 …` → 仍是串扰：查 CHIPEN / SD 是否接错脚 / 是否焊虚；
   - `raw=0000 0000 …` → 完全没有数据：查 VDD 与 GND；
   - `rms=几十~几百、clean=1` → 正常，接着测唤醒词；
5. 若 `left` 与 `right` 都是 `5555`，基本可以断定麦克风没工作（不是软件问题）。

## 13. 第三轮：`raw32=FFFFFFFF` + 孤立尖峰 —— 麦克风没有驱动 SD（v0.4.7）

### 13.1 本轮日志

```
I (1005) drv:i2s: 声道自检[left]:  rms=1365 alt_ratio=0.00 has_data=1 clean=1 raw=FFFF FFFF FFFF FFFF
I (1105) drv:i2s: 声道自检[right]: rms=965  alt_ratio=0.00 has_data=1 clean=1 raw=FFFF FFFF FFFF FFFF
I (1105) drv:i2s: 采样声道确定为 left（配置默认 left）
...
I (4545)  app:voice: mic peak=21824 (state=0)
I (10565) app:voice: mic peak=21824 (state=0)
I (13575) app:voice: mic peak=22464 (state=0)
```

### 13.2 从数字反推样本构成（关键）

`rms` 是 512 点的 AC 有效值，峰值每次都是 ~21824（≈`0x5540`）。反推：

| 通道 | rms | 总能量 = rms²×512 | 单个 21824 的能量 | 折算孤立尖峰数 |
|---|---|---|---|---|
| left | 1365 | 9.54e8 | 21824² = 4.76e8 | **≈ 2 个** |
| right | 965 | 4.77e8 | 4.76e8 | **≈ 1 个** |

结论非常明确：

```
512 个样本 = 510 个「精确等于 -1（0xFFFF）」 + 1~2 个孤立尖峰
```

- **不是语音**：语音会让几乎每个样本都变化；
- **不是时钟串扰**：串扰会逐点等幅反号（`0x5555` 家族，v0.4.6 之前的表现）；
- **是“数据线静止在 1”**，只偶尔被相位滑动打断一下。

即：**INMP441 完全没有在驱动 SD 线**（三态/高阻），ESP32 读到的是电平，不是数据。AFE 拿到的全是直流，唤醒自然永远不触发。

### 13.3 为什么 v0.4.6 的自检没报错

v0.4.6 的判据只用 `rms >= 2` 当作“有数据”的门槛。静止线的 rms=1365（被极少数尖峰抬高），于是被判为 `has_data=1, clean=1` —— **判据被“孤立尖峰”骗过**。

v0.4.7 改为统计 `stuck_ratio`（恰好等于 -1 或 0 的样本占比）：

| 场景 | stuck_ratio | 判定 |
|---|---|---|
| 麦克风未驱动（静止线） | 0.996 | 无效 |
| 正常但安静（本底噪声 σ≈2LSB） | ≈0.2 | 正常 |

阈值取 0.97，两者相差一个数量级，既能抓到静止线，也不会误杀安静环境。

### 13.4 万用表三步定位（不用示波器，2 分钟）

器件处于 3.3V 供电、正在运行的状态下，用**直流电压档**量 INMP441 的引脚对 GND：

| 测点 | 正常值 | 异常含义 |
|---|---|---|
| SCK (GPIO5) | ≈1.6~1.7 V（1.024MHz 方波的平均值） | 0 V → 引脚没输出，代码/引脚配置问题 |
| WS (GPIO4) | ≈1.6 V（16kHz 方波） | 0 V → 同上 |
| **SD (GPIO6)** | **≈1.5~1.7 V**（数据在翻转，平均值接近 VDD/2） | **恒 3.3 V 或恒 0 V → 麦克风没有驱动** |
| VDD | 3.3 V ±5% | 偏低 → 供电不足 |
| CHIPEN（若引到排针，第 8 脚） | 3.3 V | **0 V 或悬空 → 麦克风处于 power-down，SD 全程高阻** |

SD 恒为 3.3 V 就是本次 log 的直接对应现象（`0xFFFF`）。

### 13.5 硬件排查顺序（按概率）

1. **CHIPEN（第 8 脚）**：手册原文 *"When set low (ground), the microphone is disabled and put in power-down mode."*
   散装 INMP441 模块经常把这个脚悬空。有该焊盘 → **必须接 VDD**。
2. **模块丝印引脚顺序**：不同批次的 INMP441 模块，6 个焊盘的顺序不完全一致
   （有 `VDD GND SD SCK WS L/R`，也有 `VDD GND L/R SD SCK WS`）。
   **按丝印文字接，不要按记忆/按位置接**——这是最容易错、也最难自查的一项。
3. **SD 是否真的通到 GPIO6**：万用表通断档，从模块 SD 焊盘量到排针、再从排针量到 ESP32 引脚。
4. **摄像头排线**：ESP32-S3-CAM 的 `GPIO6=VSYNC / GPIO4=SIOD / GPIO5=SIOC / GPIO15=XCLK / GPIO16=D7`，
   与我们的 I2S 引脚 **完全重叠**。摄像头插着时，传感器会往 GPIO6 输出 VSYNC（约 15~60Hz），
   **这正好解释“每 32ms 有 1~2 个孤立尖峰”的节奏**。**必须拔掉排线**（不是下电，是拔掉）。
5. **SD 加 100 kΩ 下拉**到 GND：手册要求；没有下拉时悬空线更容易被 BCLK 串扰。

### 13.6 v0.4.7 新增的可观测性

| 新增 | 作用 |
|---|---|
| `stuck` / `spikes` / `dc` 三个指标 | 直接区分「静止线」「时钟串扰」「真实音频」 |
| `raw32=xxxxxxxx`（4 个 32bit 原始字） | 一眼看出是不是整字 `0xFFFFFFFF` |
| 启动打印实际生效的 6 个 I2S 引脚 | 排除“配置与接线不一致” |
| **开机蜂鸣（200ms / 880Hz）** | 独立验证 TX：听到“嘀”一声 = 功放/喇叭正常，问题只在麦克风侧 |

`menuconfig → Voice Wake System → 开机播放蜂鸣` 可关闭（默认开启）。

### 13.7 下次日志怎么读

```

drv:i2s:         raw32=ffffffff ffffffff ffffffff ffffffff
```

看到上面这三行 = 硬件问题（按 13.5 顺序查），**与固件无关**。


`raw32` 的 4 个字各不相同、且数值在几十~几千 → 麦克风正常；`clean=1` 后即可测唤醒词。

## 14. 第四轮：摄像头已拔、模块无 CHIPEN，仍是静止线（v0.4.8）

### 14.1 本轮日志与上一轮的区别

```
I (1016) drv:i2s: 声道自检[left]:  rms=0 dc=-1 stuck=1.00 alt=0.00 spikes=0 clean=0
I (1016) drv:i2s:          raw32=ffffffff ffffffff ffffffff ffffffff
I (1116) drv:i2s: 声道自检[right]: rms=0 dc=-1 stuck=1.00 alt=0.00 spikes=0 clean=0
E (1116) drv:i2s: 麦克风没有驱动 SD：GPIO6 上采到的是**静止电平**...
...
I (4776)  app:voice: mic peak=16384 (state=0)
I (10796) app:voice: mic peak=24563 (state=0)
I (23886) app:voice: mic peak=32767 (state=0)
```

两点说明：

1. **自检这次判对了**：`stuck=1.00`、`rms=0`、`raw32` 全是 `ffffffff` —— 数据线**完全静止**，一个尖峰都没有。
   比上一轮更干净，说明连“偶尔的相位滑动”都没有了，线上就是恒定的高电平。

2. **后面 `mic peak=16384~32767` 不是声音，别被误导**。
   把这几组数换成十六进制：`0x4000 / 0x5FF3 / 0x7FFF / 0x4C00 / 0x5C03`——
   **全部落在 `0x4000~0x7FFF`**，也就是最高两位是 `01`，本质是 `0x5555`（0101 图案）家族
   因采样相位滑动产生的变体。它仍然是**串扰**，不是音频。

   v0.4.8 起，这种帧不再打印 `peak`，改为每 5 秒一条：

   ```
   W app:voice: 麦克风数据无效[静止线]：SD 线上没有数据（麦克风未驱动），请检查供电/时钟/接线
   ```

### 14.2 固件时序第二次核验（结论：固件无问题）

| 检查项 | 实际取值 | 依据 | 是否符合 INMP441 |
|---|---|---|---|
| `slot_bit_width` | `AUTO` → 解析为 32（=data_bit_width） | `i2s_std.c:33-36` | ✅ |
| `total_slot` | **恒为 2**，与 mono/stereo 无关 | `i2s_std.c:105` | ✅ |
| BCLK | 16000 × 2 × 32 = **1.024 MHz** | `i2s_std.c:40` | ✅ = 64×fs |
| WS 占空 | `ws_width = 32` → 高 32 / 低 32 | `i2s_std.h:37` | ✅ 每帧 64 SCK |
| 位序 | 32bit 时 `msb_right = false` | `i2s_std.h:40` | ✅ MSB first |
| 数据取法 | 32bit 右移 16 → 高 16 位 | `audio_i2s.c` | ✅ 24bit 左对齐 |

**固件侧已经没有可疑点了。** 剩下的只能是「电/时钟/数据有没有真正到达模块」。

### 14.3 模块 6 焊盘、无 CHIPEN、摄像头已拔 → 只剩 4 个原因

| # | 原因 | 为什么会造成“静止高电平” |
|---|---|---|
| 1 | **3.3V 没到模块** | 模块掉电，SD 高阻 |
| 2 | **SCK 或 WS 没到模块**（虚接/焊盘错位） | 没有时钟 → 麦克风**不驱动 SD**，症状与掉电完全一样 |
| 3 | **SD 没到 GPIO6** | 读的是悬空脚 |
| 4 | **模块损坏 / 焊盘顺序与丝印不符** | 同上 |

> 特别注意第 2 条与**焊盘错位**的组合：如果 `SD/SCK/WS` 三个焊盘按“位置”而不是按“丝印文字”接线，
> 那么麦克风的 SD 焊盘会被 ESP32 的 BCLK 输出直接驱动（双输出对顶），
> 而 ESP32 的 GPIO6 接到的其实是麦克风的 **WS 输入脚（高阻）** → **读出来正好是恒定的高电平**。
> **这与本轮日志完全吻合，是当前最值得先排除的一项。**

### 14.4 测量位置必须是“模块自己的焊盘”

在板子排针上量是量不出问题的（线断了排针照样有信号）。**在模块的焊盘上**、设备运行中用直流档量：

| 测点（模块焊盘 → GND） | 正常值 | 异常结论 |
|---|---|---|
| VDD | 3.30 V | 0 V / 1.x V → 供电没到模块（杜邦线虚接或 VDD/GND 接反） |
| SCK | ≈1.6 V（1.024MHz 方波均值） | 0 V → SCK 没到（换线/重焊） |
| WS | ≈1.6 V（16kHz 方波均值） | 0 V → WS 没到 |
| **SD** | **≈1.5~1.7 V**（数据在翻转） | **恒 3.3 V → 麦克风没驱动（模块问题或 SD 焊盘没接对）；恒 0 V → SD 对地短路** |

### 14.5 三个最快的排除动作（按顺序，每步 ≤1 分钟）

1. **拔掉 SD 线，只留 VDD/GND/SCK/WS**，量模块 SD 焊盘：应该是悬空（读数飘）。
   再把 SD 接回 GPIO6 —— 若接回后仍是 3.3V 恒定，说明麦克风没输出。
2. **核对焊盘丝印**：用手机拍一张模块正面（能看清丝印文字）的清晰照片，
   **确认 `VDD / GND / SCK / WS / SD / L-R` 六个焊盘的实际排列顺序**，逐根对照杜邦线。
3. **换一块模块**（INMP441 模块十几块钱）。换上去 `clean=1` → 原模块损坏或丝印错位；
   仍为静止线 → 问题一定在接线/供电，不在模块。

### 14.6 修好后的判据（同一份固件，不用再改代码）

```
I drv:i2s: 声道自检[left]: rms=120~2000 dc≈-5 stuck=0.10~0.30 alt=0.00 spikes=0 clean=1
I drv:i2s:          raw32=00000a3c fffffe10 000003d8 00000f20     ← 4 个字各不相同
W app:voice: （不再出现“麦克风数据无效”）
I app:voice: mic peak=xxxx                                        ← 说话时出现，数值随音量变化
I app:voice: wake word detected                                   ← 说「小美同学」
```

只要 `raw32` 的四个字**互不相同**、`stuck < 0.5`，就说明麦克风在正常工作。

## 15. 第五轮：蜂鸣也没响 → 收发两侧同时失效，优先查共地与供电（v0.4.9）

### 15.1 新增的两条关键信息

1. **开机蜂鸣没有响** —— 说明 `I2S TX → MAX98357A → 喇叭` 也不工作。
2. **模块照片显示丝印是镜像的** —— 说明拍到的是 PCB 反面，**左右顺序与正面相反**。

### 15.2 为什么这两条信息改变了排查方向

前四轮一直在查麦克风（RX）。现在 TX 也无声，而 **RX 和 TX 唯一的共同点是电源与地**：

| 共同项 | 说明 |
|---|---|
| **GND** | 两个模块都要与 ESP32 共地；地没通 → 麦克风时钟无效（SD 高阻）+ 功放识别不到时钟（静音） |
| **3.3V / 5V** | 供电没到 → 两边同时失效 |
| 引脚本身 | 6 个 GPIO 同时坏的概率极低 |

**症状完全吻合**：麦克风 SD 恒高（无时钟不驱动）、功放完全无声。

> 所以现在的第一嫌疑从"麦克风接线"变成 **"GND 是否真的共地"**，
> 以及 **"VDD/VIN 是否真的到了模块焊盘"**。

### 15.3 丝印镜像带来的接线风险

照片里 `GND VDD SD` 与 `L/R WS SCK` 两排文字都是镜像的，按"位置"接线必然错位。
可靠的判断方式是用**邻接关系**（镜像不改变谁在中间）：

- 一排三焊盘的**中间 = VDD**，两端是 `GND` 与 `SD`；
- 另一排的**中间 = WS**，两端是 `L/R` 与 `SCK`。

### 15.4 提供两个最小验证工程

为了把"软件配置"和"硬件接线"彻底分开，新增两个独立 IDF 工程（详见 `firmware/test/README.md`）：

| 工程 | 路线 | 用法 | 判读 |
|---|---|---|---|
| `firmware/test/mic_test` | 只用 I2S0-RX，与主项目同参数 | `cd firmware/test/mic_test && idf.py set-target esp32s3 && idf.py -p COM6 build flash monitor` | 先自动扫描 `32/16bit × 左/右` 四种配置各 1 秒；`cls=正常` 且说话时 `rms` 变化 = 麦克风正常 |
| `firmware/test/amp_test` | 只用 I2S1-TX | `cd firmware/test/amp_test && ...` | 三种帧格式轮流播放，**响 1 声 = 16bit 立体声，2 声 = 单声道，3 声 = 32bit** |

两个工程都不依赖 `components/`、不含 WiFi 与 esp-sr，初始化代码与主项目逐行一致，
因此结论可以直接套回主项目。

### 15.5 建议的执行顺序（约 10 分钟）

1. **先测功放**（`amp_test`）：能出声 → TX 与 GPIO15/16/7 都没问题，
   那主项目蜂鸣没响就说明主项目的 TX 配置或音量有问题；完全没声 → 查 `VIN`/`SD_MODE`/`GND`。
2. **再测麦克风**（`mic_test`）：先看 4 种配置的扫描结果。
   若四种全是"静止"，那与固件无关，直接进硬件测量。
3. **万用表在同一时刻量这几处**（都在模块焊盘上，设备运行中）：

| 测点 | 正常 | 若不对 |
|---|---|---|
| ESP32 GND ↔ 模块 GND（通断档） | 直通（<1Ω） | **地没通 —— 这是当前头号嫌疑** |
| 模块 VDD | 3.30 V | 供电没到 |
| 模块 SCK / WS | ≈1.6 V | 0 V → 时钟没到 |
| 模块 SD | ≈1.5~1.7 V | 恒 3.3 V → 麦克风没驱动 |
| 功放 VIN | 5 V（或 3.3~5.5 V） | 0 V → 功放没供电 |
| 功放 SD_MODE | 3.3 V | 0 V → 芯片处于 shutdown，必然无声 |
| 功放 BCLK / LRC | ≈1.6 V | 0 V → 时钟没到（线没通） |

## 16. 第六轮：硬件已修复，日志解读（v0.5.0）

### 16.1 结论

接线问题解决后，`mic_test` 与 `amp_test` 均正常：

- 麦克风：**左槽有数据、右槽静止** —— 与 `L/R → GND`（左声道）完全一致，说明接线正确；
- 功放：三种帧格式都能出声，说明 `GPIO16/15/7` 与 MAX98357A 通路正常。

### 16.2 扫描结果解读（非常重要）

```
[SCAN] 32bit/left   BCLK=1024kHz cls=正常 rms=91   raw=f989 f955 f975 f97e   ← 四个字各不相同 = 真数据
[SCAN] 32bit/right  BCLK=1024kHz cls=静止  rms=0    raw=0000 0000 0000 0000   ← 右槽无数据（L/R 接地，正确）
[SCAN] 16bit/left   BCLK=512kHz  cls=正常 rms=184  raw=f833 f833 f827 f827   ← 每个样本重复两次！
[SCAN] 16bit/right  BCLK=512kHz  cls=静止  rms=0    raw=0000 0000 0000 0000
```

**`16bit/left` 那行看着 rms 更大（184 > 91），但它是错的配置**，证据就在 `raw`：

```
f833 f833 f827 f827 f827 ...     ← 相邻成对相同
```

说明麦克风实际只以 **8 kHz** 出新样本，而 ESP32 按 16 kHz 采样，于是每个样本被读两次。
原因是：INMP441 每个 WS 帧必须 64 个 SCK；`16bit` 槽宽时 BCLK = 16k×2×16 = **512 kHz**
（每帧只有 32 个 SCK），麦克风把帧长翻倍理解，输出率被砍半。

后果：音频被"降速"、频谱整体下移一个八度，唤醒词模型必然识别不到。
**所以主项目必须保持 32bit 槽宽（BCLK=1.024 MHz）**，不要为了"rms 更大"改成 16bit。

### 16.3 连续采集段为什么会看到"直流漂移"

```
 1.5s dc=-1114 min=-1432 max=-777
 8.5s dc=463   min=376   max=520
15.5s dc=806   min=752   max=848
```

连续段跑的是扫描选出的 `16bit/left`（错误配置）。帧率不匹配会让 ESP32 的读取窗口
相对麦克风的数据字**持续滑动**，于是低位一直读到位移中的垃圾位 → 表现为缓慢漂移的直流。
**这是配置错误的副产品，不是麦克风异常。**

换成 32bit 后，安静时应当是：`rms 5~50、dc 接近 0（可能有几百的固定偏置）、dup < 0.3`。
固定的直流偏置不影响识别（esp-sr 的 AFE 内部会去直流）。

### 16.4 mic_test 判据修正

原扫描只按 `rms` 打分，导致把"降速的 16bit"选成最佳。已改为：

1. 新增 `dup` 指标（成对重复比例）；
2. `cls=正常 且 dup > 0.8` 时扣 1500 分，确保 32bit 胜出；
3. 命中时打印告警：`样本成对重复(dup≈1)：该配置的 BCLK 只有一半，麦克风实际工作在 8 kHz`；
4. 连续采集行也带 `dup`，一眼能看出采样是否被降速。

### 16.5 已删除开机蜂鸣

按要求移除了整条链路：

| 文件 | 变更 |
|---|---|
| `components/vw_audio/audio_i2s.c` | 删除 `audio_i2s_boot_beep()` 实现 |
| `components/vw_audio/include/audio_i2s.h` | 删除声明 |
| `main/app_main.c` | 删除调用 |
| `main/Kconfig.projbuild` | 删除 `VW_BOOT_BEEP` 选项 |

> 若 `sdkconfig` 里还留着 `CONFIG_VW_BOOT_BEEP=y`，`idf.py reconfigure` 后会自动丢弃，无需手工处理。

### 16.6 "一直有蜂鸣"的真正根因：`auto_clear` 默认关闭

删掉蜂鸣只是去掉了音源，根因还在 —— 否则播放完一段 TTS 之后同样会长鸣。查到 IDF 的定义：

```c
/* esp_driver_i2s/include/driver/i2s_common.h:25-29 */
.dma_desc_num = 6, .dma_frame_num = 240,
.auto_clear_after_cb = false,      ← 默认关闭
```

```c
auto_clear_after_cb;  /*!< Set to auto clear DMA TX buffer after `on_sent` callback,
                            I2S will always send zero automatically if no data to send. */
```

**关闭时**：TX 没有新数据可发，DMA 就把"最后一段缓冲"**循环重发**——
蜂鸣的最后 20ms 被无限重复，听感就是持续的蜂鸣/长鸣。
**打开时**：改为自动发 0，静音才是真静音。

修复（`components/vw_audio/audio_i2s.c`）：

```c
i2s_chan_config_t chan_cfg = I2S_CHANNEL_DEFAULT_CONFIG(I2S_NUM_0, I2S_ROLE_MASTER);
chan_cfg.auto_clear = true;   // TX 无数据时发 0，而不是循环最后一段缓冲
```

RX 侧一并用同一份 `chan_cfg`，读空时拿到 0 而不是旧数据，也让"静止线"判定更可靠。

> 这个坑对后续 TTS 播放同样关键：播报结束后的静音段若不置零，
> 会持续重复最后一个音素，听起来像"喇叭卡住"。

   现在改为 `voiced = VAD || 去直流 RMS > 300`，并新增"唤醒后 3s 无人说话即结束（nospeech）"。

## 18. 界面上的白色方块与"数字看不见"（v0.7.2）

### 18.1 音量框里没有数字，只剩两个上下箭头

**现象**：设备页音量滑杆右边的小方框，只能看到 `∧ ∨`，数字是空白；端口框也偏窄。

**原因**：宽度被写死成 `setFixedWidth(64)`，但这个控件在主题 QSS 下的自然宽度（`sizeHint`）
是 **94px**。QSpinBox 内部顺序是「左边数字区 + 右边上下按钮」，宽度不够时先压缩数字区：
数字被裁掉，按钮还在，看起来就"只剩箭头"。

**排查手法**（以后遇到类似"控件内容看不见"可以直接照做）：

```python
c = page.volume_spin
print(c.width(), c.sizeHint().width())     # 64 94  → 被写死得比自然宽度还小
```

**修复**：删掉固定宽度，改为按 `sizeHint` 定宽（`device_page._fit_spin`），下限 60、上限 170。

> 顺带一条经验：**不要用 QSS 去接管 QSpinBox 的 `::up-button` / `::down-button`**。
> 一旦写了这两个子控件，Qt 就不再绘制原生箭头，而"用 border 三角拼箭头"的写法在
> QSpinBox 上并不生效（实测箭头整块消失）。要么完全不管按钮、只把宽度算足，要么就必须
> 提供箭头图片。

### 18.2 窗口最右侧中部有个白色小块

**现象**：窗口右侧那条窄栏，垂直中部有一小块白色，里面像是有个残缺的图标。

**原因**（两个问题叠加）：

1. 折叠栏宽度只有 40px，减掉左右各 10px 边距只剩 **20px**，而这一行里先放了标题
   「运行状态」再放按钮 —— 标题把空间吃光，按钮被挤到 **5px 宽**：

   ```python
   print(btn.geometry().getRect())   # (24, 294, 5, 23)   ← 5px
   ```

2. 这个按钮的 `objectName` 是空串，而 QSS 里只写了 `QToolButton#nav`，于是它走
   **系统原生样式**——在深色主题上就是一块浅色（白）底。

**修复**：

- QSS 增加一条全局 `QToolButton { background: transparent; ... }`，
  `#nav` 用 ID 选择器优先级更高的规则覆盖它，互不影响；
- 标题与按钮分开：折叠时隐藏标题、按钮固定 `24x24`，栏宽 40→44px（44-20=24 刚好放下）；
- 折叠时对右侧栏的 `QVBoxLayout` 调 `setAlignment(Qt.AlignTop)` ——
  body 隐藏后布局里只剩一项，`QVBoxLayout` 会把它**垂直居中**（实测 y=294/612），
  不显式顶部对齐就会跑到中间去。

### 18.3 右侧那条浅色竖条

滚动条只写了 `::handle`，没写 `::add-page` / `::sub-page`，未定义的子控件由系统样式
补一块浅灰底。补上 `background: transparent` 即可。

同理，`QCheckBox::indicator` 不写样式时也是系统浅灰方框，在深色底上很扎眼——
需要自己给一个深色圆角框；勾选态的**对勾** QSS 画不出来，用 `icons.pixmap("check", ...)`
渲染成 PNG 再 `image: url(...)` 引用。

### 18.4 一句话规律

> 深色主题下凡是出现"白色块"，基本都是**没被 QSS 覆盖到的原生子控件**。
> 排查顺序：`objectName` 是不是空 → QSS 有没有对应选择器 →
> 子控件（`::indicator`/`::handle`/`::add-page`/`::up-button`）有没有漏写。
