# 变更记录

## v0.8.1（2026-10-25）蓝牙按需初始化：修复 playback 任务创建失败

### 现象（真机日志）

```
I (923)  main: voice wake system boot (fw 0.5.0), free_heap=8584084
...
E (1653) app:voice: [0x0101:NO_MEM] create playback task failed
E (1653) main: [0x0103:BOOT_FAIL] ... 系统进入故障保持
```

8.5MB 空闲内存却创建不了 4KB 栈的任务。

### 根因

`free_heap` **包含 PSRAM**；`xTaskCreate` 的任务栈**只能来自内部 RAM**（约 248KB）。
v0.8.0 在开机时就 `ble_prov_init()`，NimBLE 占走约 50KB 内部 RAM，
排在最后的 playback 任务栈分配失败。

### 修复

| 改动 | 说明 |
|---|---|
| 蓝牙改**按需初始化** | 开机不再调 `ble_prov_init()`；进入配网时 `ble_prov_start()` 内部自动初始化 |
| 新增 `ble_prov_deinit()` | `nimble_port_stop` → `nimble_port_deinit` → 控制器 disable/deinit → `esp_bt_mem_release(ESP_BT_MODE_BLE)`，把约 50KB 还给堆；配网超时退出时调用 |
| playback/audio 创建顺序对调 | 内部 RAM 最紧张的时刻留给 playback，失败日志更真实 |
| 失败日志带 `free_internal` | `heap_caps_get_free_size(MALLOC_CAP_INTERNAL)`，以后一眼看清 |

### 顺带确认（日志解读）

- BLE 广播链路已跑通（`BLE 就绪，设备名 VoiceWake-457B3C` → `advertise`）；
- 广播名后缀 `457B3C` = WiFi MAC `28:84:85:45:7b:3c` 后三字节 ✓（蓝牙 MAC 是 `...7b:3e`，两者本来就不同）；
- **唤醒词模型对不上**：srmodels.bin 里只有 `wn9_xiaomeitongxue_tts`，
  配置的 `wn9_hilexin` 不存在 → 已自动回退（`srv:wake` 有警告）。
  要么喊"小美同学"，要么 `idf.py menuconfig` 改回 hilexin 并重烧（srmodels 随 `idf.py flash` 更新）。


## v0.8.0（2026-10-25）蓝牙（BLE）配网取代 AP 热点 + hello 参数变更重发

### 为什么换掉 AP 配网

原「AP 配网兜底」**实际是失效的**：设备开热点时没有 TCP 连接，
而设备页的 `wifi.set` 恰恰要靠这条 TCP 发出去（`_send_command` 在 `conn is None` 时直接 return）。
也就是说在最需要配网的时刻，配置永远发不出去，界面却显示"已下发，等待设备重启重连"。

### 决策（用户确认）

| 决策点 | 结论 |
|---|---|
| 进入时机 | 凭证为空 → **立即进**；有凭证但连续失败 `VW_STA_FAIL_THRESHOLD`(5) 次 → 进 |
| 退出时机 | 配网窗口 `VW_PROV_TIMEOUT_S`(300s) 无有效配置 → 超时退出，回 WiFi 重连 |
| WiFi 信号行 | **保留**（用户明确要求不删） |

### 硬件评估结论（先查后做）

- BLE 用片内射频，**不占 GPIO**，与 I2S 引脚（4/5/6/7/15/16）无冲突；
- 真正的风险是**射频共存**（WiFi/BLE 共用 2.4G 天线）与**BLE 控制器任务抢占音频任务**，
  对策：只在配网窗口广播 + 成功后真正停广播（成功路径重启）；
- 空间实测：app 1.01MB / 分区 3MB（NimBLE 约再 +0.4MB），静态 DRAM 50KB / 512KB，余量充足。

### 固件改动

| 文件 | 变更 |
|---|---|
| `components/vw_prov/`（新增） | NimBLE GATT：CFG 写入（SSID/密码/上位机 IP/端口）+ STATE 读/通知；广播名 `VoiceWake-XXXX`（MAC 后三字节）；MTU 185；未启用 NimBLE 时编译为空实现 |
| `components/vw_comm/wifi_client.c` | **删除 AP 模式**；无凭证返回 `ESP_ERR_NOT_FOUND`；新增失败计数回调 `wifi_fail_cb`、`reconnect_with()`（配网后立即验证）、`wait_ip()`、`ip()`、`retry_now()` |
| `components/vw_voice/voice_service.c` | 配网状态机（prov 任务 + 队列）：进/出配网、写 NVS、`reconnect_with` + 15s 等 IP、`ok`→停蓝牙→重启 / `fail`→保持蓝牙；新命令 `prov.start`；`status.get` 的 `ap_mode` → `prov` |
| `components/vw_utils/` | 新增错误码 `0x3004 BLE_INIT` / `0x3005 BLE_GAP` / `0x3006 BLE_PROV_FAIL` |
| `main/Kconfig.projbuild` | 新增 `VW_PROV_ENABLE / VW_PROV_NAME_PREFIX / VW_PROV_TIMEOUT_S / VW_STA_FAIL_THRESHOLD` |
| `sdkconfig.defaults` | NimBLE + 角色裁剪 + `ESP_COEX_SW_COEXIST_ENABLE` |

**配网成功路径**：写入 NVS → `reconnect_with` 立即验证 → 拿到 IP → 推送 `ok` → 停广播 → 800ms →
`esp_restart()`（让新的 host_ip/port 生效，并彻底关闭蓝牙射频）。
失败路径：推送 `fail`，蓝牙保持，用户改密码重写，不用重启设备。

### hello 变更重发（用户要求的任务 2）

- `send_hello()` 从 `on_conn_change` 抽出，`config.set` / `volume.set` / `wakeword.set`
  成功后**补发一次**（新增 `wake_enable` / `ack_enable` 字段）；
- 上位机 `pipeline._on_control` 用 `_hello_seen` 区分首次（"设备上线"）与后续（"设备信息已同步"），
  避免每次调音量都误报"设备上线"。

### 顺带修掉的两个存量 bug

1. **`config.set` 一直忽略 `host` 字段**——设备页「下发配置」里的上位机 IP/端口其实从未生效过，
   固件现在会解析并写 NVS；
2. **`config.get` 应答回填错位**——固件返回扁平的 `host_ip/host_port`，
   上位机却按嵌套 `host` 对象取，导致"读取当前配置"永远读不回 IP/端口。

## v0.7.0（2026-10-24）播报"飞快"根因修复 + 唤醒回复词

### 问题 1：TTS 播报语速极快（"1 秒说完 10 秒的话"）

**排查过程（先证伪，再定位）**

| 环节 | 实测 | 结论 |
|---|---|---|
| 上位机 TTS | 29 字文本 → **5.07 s** @16k（合成 4.0s） | 语速正常，**不是 TTS / 重采样问题** |
| 下发帧数 | 5.07s = **253 帧**，一次性推完（几十 ms） | 远超设备缓冲 |
| 设备播放队列 | `xQueueCreate(8)`，`xQueueSend(..., 0)` | **队列满即静默丢弃** |

**根因**：上位机在极短时间内灌入 253 帧，设备只能接收约 8 帧（160ms），其余 245 帧被丢；
听感就是"整段话一瞬间念完"。与采样率、Piper 语速、音量都无关。

**修复**

| 位置 | 修改 |
|---|---|
| `host/voice_assistant/pipeline.py` `_send_audio_frames` | **按实时节奏下发**：每帧 20ms，保持领先播放进度 150ms（`asyncio.sleep` 补时），既不断流也不丢帧 |
| `firmware/components/vw_voice/voice_service.c` | 播放队列 **8 → 40 帧**（≈800ms 抖动缓冲）；入队超时 **0 → 10ms**（轻微背压）；丢帧时打限频告警 `播放队列满，丢弃一帧` |

### 问题 2：唤醒回复词（"在的"）

**时序**（详见 `docs/01_接口设计.md` §5.4）

```
设备：唤醒命中 → session.start{need_ack:true} → APP_ACK_WAIT（最长 4s）
上位机：立即合成 ack_text → AUDIO_DOWN(同一 session_id)
设备：收到 END 且播完 → APP_CAPTURE → 开始上行音频
```

**下位机**
- 状态机新增 `APP_ACK_WAIT`：唤醒后先等回复词，**播完才采集**，避免把自己的回声录进去；
- `ACK_TIMEOUT_MS = 4000` 超时兜底：上位机没响应也会照常进入采集，不会卡死；
- `config_store` 新增 `ack_enable`（NVS 键 `ack_en`，默认 true）；
- `config.get / config.set / status.get` 支持 `ack_enable`。

**上位机**
- `pipeline._send_ack()`：收到 `need_ack` 立即 TTS 合成并限速下发；未启用/合成失败时发**空 END 帧**让设备立刻采集；
- `config.py` `DeviceConfig` 新增 `ack_enable`（下发设备）与 `ack_text`（仅本机合成，不下发）；
- 设备页新增「唤醒回复词」开关 + 「回复词文本」输入框（默认"在的"）；`config.set` 带上 `ack_enable`。

### 验证
- 限速：1.0s 音频下发耗时 **0.85s**、**50 帧**（= 20ms/帧 + 150ms 预冲）；
- 回复词"在的"：**30 帧 ≈ 0.6s**，首帧 `START`、末帧 `END` 正确；
- `pyflakes` 0 warning、`py_compile` 通过；
- 固件括号/枚举分支检查通过（4 个状态齐全）。

### 需要重新烧录
本轮固件有改动（状态机 + 队列），必须 `idf.py build flash`；上位机重启即可。

### 关键发现（来自 mic_test 日志）
`16bit/left` 的 rms(184) 大于 `32bit/left`(91)，但**前者是错误配置**：

```
16bit/left  raw=f833 f833 f827 f827   ← 相邻成对重复 = 实际采样 8kHz
32bit/left  raw=f989 f955 f975 f97e   ← 四个各不相同 = 正确的 16kHz
```

INMP441 要求每帧 64 个 SCK。16bit 槽宽时 BCLK=512kHz（每帧仅 32 SCK），
麦克风光标输出率被砍半，音频降速一个八度，唤醒不可能成功。
**主项目保持 32bit 槽宽（BCLK=1.024MHz）不变。**

另：连续采集段出现的"直流漂移"（dc 从 -1114 到 +806）也是错误配置下
读取窗口相对数据字滑动造成的假象，非麦克风异常。

## v0.4.8（2026-10-24）运行期麦克风数据质量判定 + 去掉 peak 日志的误导

### 现象
摄像头排线已拔、模块为 6 焊盘（无 CHIPEN），自检仍报 `stuck=1.00 / rms=0 / raw32=ffffffff`
（静止线，判定正确）。但随后 `mic peak` 又打印 `16384 / 24563 / 32767` 等数值，
看起来"声音很大"，与"麦克风没数据"的结论矛盾，容易误导排查方向。

### 分析
把这些峰值换成十六进制：`0x4000 / 0x5FF3 / 0x7FFF / 0x4C00` —— 全部落在 `0x4000~0x7FFF`，
即最高两位恒为 `01`，是 `0x5555`（0101 图案）家族因采样相位滑动产生的变体。
**仍然是 BCLK 串扰，不是音频。** 旧代码只看峰值大小，把它当成"有声音"。

同时二次核验固件时序，确认无问题：

| 检查项 | 取值 | 依据 |
|---|---|---|
| `slot_bit_width` | AUTO → 32 | `i2s_std.c:33-36` |
| `total_slot` | 恒为 2（与 mono/stereo 无关） | `i2s_std.c:105` |
| BCLK | 16000×2×32 = 1.024 MHz | `i2s_std.c:40` |
| `ws_width` | 32 → WS 50% 占空，每帧 64 SCK | `i2s_std.h:37` |
| `msb_right` | 32bit 时为 false（MSB first） | `i2s_std.h:40` |

### 修改
| 文件 | 变更 |
|---|---|
| `components/vw_audio/audio_i2s.c` | 新增 `audio_i2s_check_frame()`：逐帧判定 `OK / STUCK / CROSSTALK`（静止线 97% 规则 + 等幅反号 80% 规则），开销极小 |
| `components/vw_audio/include/audio_i2s.h` | 声明 `audio_line_state_t` 与 `audio_i2s_check_frame()` |
| `components/vw_voice/voice_service.c` | 麦克风自检改为先判质量：无效帧**不再打印 peak**，改为每 5s 一条 `麦克风数据无效[静止线/时钟串扰]`；只有真实音频才打印 `mic peak` |
| `docs/05_故障排查.md` | 新增第 14 章：两轮日志对比、固件时序二次核验、只剩的 4 个物理原因、**必须量模块焊盘而不是排针**、焊盘错位（SD/SCK/WS 按位置接反）为何正好表现为恒定高电平 |

### 结论
固件侧所有可疑点已排除（时钟、帧格式、位序、槽位、判据）。
问题定位到「电/时钟/数据是否真正到达麦克风」，最可能是 **SD/SCK/WS 三个焊盘按位置接错**
（表现为 ESP32 的 DIN 脚接到麦克风的高阻输入脚 → 恒定高电平）。


## v0.4.7（2026-10-24）自检判据修正 + 开机蜂鸣 + 静止线诊断

### 现象
烧录 v0.4.6 后，自检两行都报 `has_data=1 clean=1`（看起来"正常"），
但 `mic peak` 稳定在 `21824/22464` 这类数值上，说「小美同学」仍不唤醒。

### 根因（数值反推）
`rms` 是 512 点 AC 有效值，峰值 ~21824：

| 通道 | rms | 总能量 | ÷ 单个峰值能量 | 孤立尖峰数 |
|---|---|---|---|---|
| left | 1365 | 9.54e8 | 4.76e8 | ≈2 |
| right | 965 | 4.77e8 | 4.76e8 | ≈1 |

即 **510/512 个样本精确等于 -1（`0xFFFF`）+ 1~2 个孤立尖峰**。

这是「数据线静止在 1」的特征，不是语音、也不是逐点反号的时钟串扰 →
**INMP441 根本没有驱动 SD 线**（三态/高阻）。

v0.4.6 的判据 `rms >= 2` 被这 1~2 个尖峰骗过（rms 被抬到 1365），所以误报"正常"。

### 修改
| 文件 | 变更 |
|---|---|
| `components/vw_audio/audio_i2s.c` | 自检新增 `stuck_ratio`（精确等于 -1/0 的占比）、`dc`、`spikes` 统计；判据改为 `stuck_ratio < 0.97`；打印 `raw32` 4 个 32bit 原始字；两槽均无效时区分「静止线」与「时钟串扰」并给出针对性提示 |
| `components/vw_audio/audio_i2s.c` | 新增 `audio_i2s_boot_beep()`：开机 200ms/880Hz 提示音，用于独立验证 TX（功放+喇叭）通路 |
| `components/vw_audio/include/audio_i2s.h` | 声明 `audio_i2s_boot_beep()` |
| `main/app_main.c` | `audio_i2s_init()` 之后调用开机蜂鸣 |
| `main/Kconfig.projbuild` | 新增 `VW_BOOT_BEEP`（默认 y）；启动日志打印实际生效的 6 个 I2S 引脚 |
| `docs/05_故障排查.md` | 新增第 13 章：数值反推、万用表三步定位、硬件排查顺序（CHIPEN / 引脚顺序 / 通断 / 摄像头 VSYNC 抢线 / 下拉电阻）、新日志判读 |

### 结论
本轮不是软件问题：**麦克风侧没有输出数据**。
按 `docs/05_故障排查.md` 13.5 的顺序查硬件即可，重点是 CHIPEN、模块丝印引脚顺序、
以及**拔掉摄像头排线**（GPIO6=VSYNC 与麦克风 SD 抢线，正好能解释那个 15~60Hz 的孤立尖峰节奏）。


## v0.4.6（2026-10-24）声道自检失效修复（DMA 预填充导致 rms=0 漏判）

### 现象
v0.4.5 烧录后自检只打印一行 `声道自检: rms=0 alt_ratio=0.00`，没有换槽；
随后 `mic peak` 仍是 `21845`（0x5555 串扰），唤醒不触发。

### 根因
`i2s_channel_enable()` 之后 DMA 缓冲里是全 0，自检紧接着读到的就是这块 0 数据：
- `rms=0` → `alt_ratio=0` → 判定“不像串扰” → 直接认定当前槽正常，从未测另一个槽。
另外判据只看“是否串扰”，没覆盖“完全没有数据（rms==0）”这种情况。

### 修改（`components/vw_audio/audio_i2s.c`）
- 新增 `probe_slot()`：切换槽位后 `vTaskDelay(60ms)`，**丢弃第一块 DMA 数据**，
  再等 40 ms 采有效样本；
- 判据拆成两条：`has_data`（RMS ≥ 2）+ `clean`（非等幅反号串扰）；
- `rx_autodetect_slot()` 改为**两个槽都测**并并排打印，选第一个 `clean` 的；
  两槽都不 clean 时报错并列出硬件清单（VDD / CHIPEN / SD 接线 / 100kΩ 下拉 / L-R）；
- 日志新增 `raw=xxxx xxxx xxxx xxxx`（前 4 样本十六进制），
  可直接区分 `5555`（串扰）、`0000`（无数据）、真实音频。

### 现场接线结论（用户提供）
- INMP441 的 VDD/GND/SCK/WS/SD/L-R 接线与固件配置**完全一致**；
- **CHIPEN（第 8 脚）未提及** → 首要嫌疑（低=断电，SD 三态 = 0x5555 串扰）；
- 建议 SD 加 100 kΩ 下拉；
- MAX98357A 的 GAIN→GND 对应 12 dB（正常），SD_MODE→3.3V 正常；
  但 VIN 建议接 5 V（3.3 V 驱动 8 Ω 只有约 0.4 W）；
- ⚠️ **ESP32-S3-CAM 的 DVP 引脚（XCLK15/SIOD4/SIOC5/VSYNC6/HREF7/D7=16）与本项目
  I2S 引脚完全重叠**，摄像头排线必须拔掉。

## v0.4.5（2026-10-24）麦克风声道自动检测（唤醒不触发）

### 现象
链路已稳定（`host connected` 后不再断开），但 `mic peak` 恒为
`21845/21846/22528/32768` 一类数值，说唤醒词无 `wake word detected`。

### 分析
峰值换算十六进制后全是 `0x5555 / 0xAAAA / 0x2AAA` 家族 —— 即 `0101…` 图案，
且连续几十秒每帧几乎不变。真实麦克风不可能帧帧等幅反号，
这是 **读错 I2S 槽位（或 SD 未接 / 未供电 / CHIPEN 未拉高）导致数据线三态、
拾取 BCLK 串扰** 的典型特征。INMP441 只在属于自己的半帧驱动 SD，另一槽三态；
读错槽 = 读噪声 → AFE 永远收不到语音。

> 手册补充：INMP441 第 8 脚 CHIPEN 低电平=断电，必须接 VDD。散装模块 CHIPEN 悬空时

## v0.4.4（2026-10-24）链路反复连断（2s 周期）修复 + 时间戳溢出修复

### 现象
上下位机每 2 秒建立一次连接又立刻断开，上位机日志 `device connected → disconnected` 循环，
下位机日志 `connected to ... → recv closed (-1)` 循环（间隔恒为 2010 ms）。

### 根因（三层）
1. **recv 超时被当成断线**：`SO_RCVTIMEO = 2s`，空闲时 `recv()` 返回 `-1/EAGAIN`，
   旧代码 `if (n <= 0) break;` 把「暂时没数据」判成「对端关闭」→ 每 2s 自断一次。
2. **存活判定只看收**：`last_recv_ms` 超过 12s 即判超时，而上位机从不回心跳，
   空闲链路即使修掉 (1) 也会在第 12 秒断一次。
3. **上位机时间戳溢出（潜在致命）**：`protocol.now_ms()` 返回 Unix 纪元毫秒（~1.76e12），
   帧头 `ts` 是 32 位，`struct.pack(">I")` 直接抛 `struct.error`。
   此前上位机从未主动发包（心跳没人回、配置没人点），所以一直没暴露；
   修好心跳应答后这条必然触发。

### 修改
- `components/vw_comm/net_client.c`
  - `recv_task`：`n > 0` 处理数据；`n < 0` 且 `errno ∈ {EAGAIN, EWOULDBLOCK, EINTR}` → 继续；
    仅 `n == 0` 或真实错误才断开。
  - 新增 `last_tx_ms`，`send_frame()` 成功后刷新；存活判定改为
    `now - max(last_recv_ms, last_tx_ms) > HB_TIMEOUT`。
- `voice_assistant/protocol.py`
  - `now_ms()` 改为**自进程启动的毫秒**（`monotonic` 差值），语义与固件一致；
  - `build_frame()` 对 `seq`/`ts` 做 `& 0xFFFFFFFF` 掩码。
- `voice_assistant/pipeline.py`：新增 `TYPE_HEARTBEAT` 分支与 `_reply_heartbeat()`，
  收到心跳即回一帧（`asyncio.create_task`），让双向都有流量。

### 验证
真实 socket 回环测试：下位机侧发 `TYPE_HEARTBEAT`，上位机回帧，客户端解析到
`HEARTBEAT REPLY TYPES: [4]`。`pyflakes` 全仓 0 warning。

### 升级注意
本轮固件侧有改动，需重新 `idf.py flash`；上位机为 Python，重启 `python main.py` 即可。

## v0.4.1（2026-10-24）AFE feed 误报修复 + I2S 时钟/帧格式校正

### 现象
v0.4.0 后启动正常（`Successfully load srmodels`、`afe ready`、WiFi 连接成功），
但每 10–30 ms 打印一次 `E srv:wake: [0x2002:AFE_FEED] afe feed failed`。

### 根因
1. **feed 返回值判错**：`esp_afe_sr_iface_op_feed_t` 文档写明 `@return The size of input`（正值），
   旧代码用 `!= 0` 判断 → 每帧必然误报。改为 `< 0` 才算失败，并首次打印返回值确认。
2. **INMP441 采样时钟不合规**：手册要求 `fSCK = 64 × fWS`（每帧 64 个 SCK）。
   原 RX 用 16bit 槽宽，IDF 驱动算出 BCLK = fS × 2 × 16 = 32×fS（只有一半），
   麦克风帧无法对齐 → 读到静音/噪声，唤醒不可能触发。
3. **MAX98357A 帧格式不完整**：原 TX 用 16bit 单声道，右槽无数据；SD_MODE 若接 (L+R)/2 会幅度减半或无声。

### 修改
- `components/vw_wakeword/wakeword.c`：`feed()` → `int fed`，`fed < 0` 判错；新增首次成功日志
  `afe feed ok: ret=... (feed_chunk=..., ch=...)`。
- `components/vw_audio/audio_i2s.c/.h`：
  - RX 改 **32bit 槽宽 + 单声道**（BCLK = 64×fS = 1.024 MHz @16 kHz），
    读 32bit 后 `>>16` 转 16bit；新增 `slot_mask` 左/右可配；
  - TX 改 **16bit 立体声**，单声道样本复制到 L/R 两槽；
  - 新增 `MAX_FRAME_SAMPLES` 上限与参数校验，内部转换缓冲用 `heap_caps_malloc(INTERNAL)`。
- `main/Kconfig.projbuild`：新增 `INMP441 L/R 声道`（左/右）选择项。
- `docs/01_接口设计.md`：8.2 音频参数表更新（RX 时钟、TX 帧格式、AFE 2 通道说明）。
- `docs/05_故障排查.md`：新增第 7 章（feed 误报、时钟核对、通道数对照、麦克风硬件清单）。

### 观察项
- 本轮日志中模型仍是 `wn9_xiaomeitongxue_tts`，说明 `sdkconfig` 未重新生成，
  `sdkconfig.defaults` 里的 `SR_WN_WN9_HILEXIN` 未生效；回退逻辑按设计工作（无崩溃）。

## v0.4.0（2026-10-24）唤醒初始化崩溃（无限重启）修复

### 现象
串口在 `AFE_SR: wakenet_init: 1` 后立即 `LoadProhibited`，`PC=afe_create_from_config(esp_afe_sr.c:337)`、`EXCVADDR=0x0`，复位类型 `RTC_SW_CPU_RST`，形成重启循环。

### 根因（三层）
1. **P0 未调用 `esp_srmodel_init("model")`**：S3 上唤醒模型不编译进 `libwakenet.a`，而是打包成 `srmodels.bin` 烧到 model 分区，运行期必须 mmap 注册后 `esp_wn_handle_from_name()` 才能取到模型。旧代码直接传入模型名就建 AFE → 库内模型表为 NULL → 内部 `memcpy` 空指针。**证据：日志中完全没有 `MODEL_LOADER` 的输出。**
2. **P0 model 分区 3 MB < `srmodels.bin` 3.81 MB**：其中 MultiNet 中文命令词 `mn6_cn` 占 3.6 MB（本项目未用），导致烧录溢出覆盖 `ota_0` 起始 830 KB，且 mmap 无法覆盖全部模型。
3. **P1 资源与配置漂移**：PSRAM 未开启（`CONFIG_SPIRAM is not set`）、data cache 32 KB/line 32 B（esp-sr 要求 64 KB/64 B）、flash 声明 8 MB 而实际 16 MB、`sdkconfig` 已生成导致 `sdkconfig.defaults` 改动未生效（实际唤醒词是「小美同学」而非「Hi 乐鑫」）。

### 修改
- `components/vw_wakeword/wakeword.c`：先 `esp_srmodel_init(CONFIG_VW_SR_MODEL_PARTITION)` → 打印分区内全部模型 → 按「Kconfig 名 → `WAKENET_MODEL_NAME` → 分区首个 `wn*`」回退解析 → 再 `create_from_config`；新增 feed/channel 参数校验；buffer 改 `calloc`；`deinit` 释放模型表；新增 `wakeword_model_name()`。
- `partitions.csv`：按 16 MB 重排，`model` 扩至 4 MB（0x310000–0x710000），app 分区各 3 MB。
- `sdkconfig.defaults`：`ESPTOOLPY_FLASHSIZE_16MB`、`SPIRAM=y/MODE_OCT/SPEED_80M/USE_MALLOC`、`DATA_CACHE_64KB`、`DATA_CACHE_LINE_64B`、`INSTRUCTION_CACHE_32KB`、`MODEL_IN_FLASH=y`、`SR_WN_WN9_HILEXIN=y`、`SR_MN_CN_NONE=y`。
- `main/Kconfig.projbuild`：新增 `VW_SR_MODEL_PARTITION`、`VW_SR_WAKENET_NAME`、AFE 模式（HIGH_PERF/LOW_COST）与内存策略三选一。
- `main/app_main.c`：启动打印复位原因与 free heap；初始化失败由 `ESP_ERROR_CHECK`（abort→panic→重启）改为「故障保持 + 周期提示」。
- `components/vw_utils`：新增错误码 `BOOT_FAIL(0x0103)`、`SR_MODEL_NOT_FOUND(0x2003)`。
- 新增 `docs/05_故障排查.md`：崩溃时序、三层根因、修复清单、整片重烧步骤、常见问题速查。
