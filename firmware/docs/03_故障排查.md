## 1. 反复重启（启动循环）

**日志特征**

```
ESP-ROM:esp32s3-20210327
Build:Mar 27 2021
rst:0xc (RTC_SW_CPU_RST),boot:0x8 (SPI_FAST_FLASH_BOOT)
...
Guru Meditation Error: Core  0 panic'ed (LoadProhibited). Exception was unhandled.
Backtrace: 0x... 0x... 0x...
```

同一段日志每 1~3 秒重复一次，且每次的 `rst:` 都是 `RTC_SW_CPU_RST` 或 `WDT`。

**根因（按概率排序）**

1. **`model` 分区为空 / 没烧 `srmodels.bin`**
   esp-sr 在 S3 上把唤醒模型打包成 `srmodels.bin` 烧到单独的 `model` 分区，
   **不编译进 libwakenet.a**。只用 `idf.py app-flash` 时 app 更新了、model 分区还是空的，
   `esp_srmodel_init("model")` 拿不到模型 → `afe_create_from_config()` 里
   `wakenet_handle` 为 NULL → `LoadProhibited`。

   ```bash
   idf.py -p COMx flash        # 必须整片 flash，不能 app-flash
   ```

2. **`model` 分区小于 `srmodels.bin`**
   分区 3MB、`srmodels.bin` 3.81MB 时只能 mmap 到一部分，模型句柄解析到越界指针。
   本工程已把 `model` 扩到 **4MB**（`partitions.csv`）：

   ```
   model,    data, spiffs,   0x310000, 0x400000,
   ```

   校验：

   ```bash
   ls -l build/srmodels/srmodels.bin      # 必须 < 4MB
   ```

3. **PSRAM 未开启 / 模式选错**
   AFE 高性能模式强依赖 PSRAM。板子是 Quad PSRAM（N8R2 类）却配了 `SPIRAM_MODE_OCT`，
   PSRAM 初始化失败 → `abort`。核对 `sdkconfig.defaults`：

   ```
   CONFIG_SPIRAM=y
   CONFIG_SPIRAM_MODE_OCT=y      # Quad 板改成 CONFIG_SPIRAM_MODE_QUAD=y
   CONFIG_SPIRAM_SPEED_80M=y
   ```

4. **data cache 不够**：esp-sr 要求 ≥ 64KB + cache line 64B，否则报警告并拖慢 WakeNet：

   ```
   CONFIG_ESP32S3_DATA_CACHE_64KB=y
   CONFIG_ESP32S3_DATA_CACHE_LINE_64B=y
   ```

5. **分区表改过但没擦 flash**：`idf.py -p COMx erase-flash` 后重新 `flash`。

**处理顺序**

```bash
cd firmware
rm -f sdkconfig                 # sdkconfig 已存在时不会套用 defaults 的新增项
idf.py set-target esp32s3
idf.py reconfigure
idf.py menuconfig               # 核对 PSRAM / cache / flash 16MB / 唤醒模型
idf.py build
ls -l build/srmodels/srmodels.bin
idf.py -p COMx erase-flash
idf.py -p COMx flash monitor
```

## 2. 初始化失败，进入故障保持

**日志特征**

```
E (412) main: [0x0103:BOOT_FAIL] 初始化失败于 audio_i2s_init: ESP_ERR_INVALID_STATE(0x103)，
              系统进入故障保持（不会重启）
E (412) main: 排查顺序：1) model 分区是否已烧录 srmodels.bin 2) 分区体积是否 >= srmodels.bin
              3) PSRAM 是否开启(Octal/80MHz) 4) data cache 是否 64KB/line 64B
E (30412) main: 仍处于故障保持状态：audio_i2s_init 失败，free_heap=xxxxx
```

**这是刻意行为，不是 bug。** 早期版本用 `ESP_ERROR_CHECK` 包装，一次失败就 `abort()` →
重启 → 又失败，形成循环，现场被冲掉。现在保持运行，方便看清楚到底哪一步失败。

看点：`初始化失败于 <阶段>` 直接告诉你是 `config_store_init` / `audio_i2s_init` /
`voice_service_init` 中的哪一个。

| 失败阶段 | 常见原因 |
|---|---|
| `config_store_init` | NVS 分区损坏 → 日志会有 `nvs_flash_erase` 提示，会自动重建一次 |
| `audio_i2s_init` | 引脚被占用（摄像头排线没拔）、I2S 通道号冲突、GPIO 号配错 |
| `voice_service_init` | 唤醒模型加载失败、WiFi 初始化失败、任务创建失败（内存不足） |

修复后 **必须复位**（`idf.py monitor` 里按 `Ctrl+]` 退出，然后 `Ctrl+T Ctrl+R` 或按 RST 键）。

## 3. 编译期 esp-sr 接口不匹配

**报错**

```
fatal error: esp_sr.h: No such file or directory
implicit declaration of function 'afe_create_from_config'
'ESP_AFE_SR_HANDLE' undeclared
```

**原因**：esp-sr **1.x** 只有 AFE 接口（`esp_afe_sr_iface.h` / `esp_afe_sr_models.h` /
`esp_afe_config.h`），`esp_sr.h` 是 esp-sr 2.x（未发布分支）的统一 API。
网上大量示例是 2.x 写法，直接照抄会失败。

**本工程的写法**（`components/vw_wakeword/wakeword.c`）：

```c
#include "esp_afe_sr_iface.h"
#include "esp_afe_sr_models.h"
#include "esp_afe_config.h"
#include "model_path.h"          /* esp_srmodel_init / esp_srmodel_get_wake_words */

srmodel_list_t *models = esp_srmodel_init(CONFIG_VW_SR_MODEL_PARTITION);
/* 逐个比对 CONFIG_VW_SR_WAKENET_NAME，找不到就用第一个 wn*，并把可用列表打日志 */
const esp_afe_sr_iface_t *afe = &ESP_AFE_SR_HANDLE;
afe_data = afe->create_from_config(&afe_config);
```

**另一个高频坑：`feed()` 返回值**

```c
int ret = afe->feed(afe_data, buf);
if (ret < 0) { ... }        // ✅ 返回的是"消耗的输入样本数"（正数）
// if (ret != 0) { ... }    // ❌ 每帧都报错，日志被刷爆
```

**版本核对**

```bash
cat firmware/dependencies.lock | grep -A2 esp-sr     # 应为 1.9.x
```

## 4. `CONFIG_VW_*` 未定义

**报错**：`'CONFIG_VW_MIC_BCLK_GPIO' undeclared`

**原因**：`Kconfig.projbuild` 放错位置。IDF 只在**组件目录**里加载 `Kconfig`/`Kconfig.projbuild`，
放工程根目录不会生效。本工程正确位置是：

```

```

改完要 `idf.py reconfigure`（或 `fullclean` 后重来），并确认：

```bash
grep VW_MIC_BCLK firmware/sdkconfig
```

## 5. 唤醒不触发之一：麦克风没进来

**判据**：说话时串口**完全没有** `mic peak=...` 日志（该日志阈值为峰值 > 1500，限频 2s 一次）。

**排查顺序**

1. **先单独验证麦克风**——用 `test/mic_test/` 独立工程，不要在有业务逻辑的固件里猜：

   ```bash
   cd firmware/test/mic_test
   idf.py set-target esp32s3 && idf.py -p COMx flash monitor
   ```

   它会自动扫 `32/16bit × 左/右槽`，输出每组的 `rms / peak / dup / cls`：

   | 输出 | 含义 |
   |---|---|
   | `cls=正常` 且 `rms` 随说话变化 | 这一组参数就是对的，把 `VW_MIC_SLOT` 固定下来 |
   | `cls=静止` | SD 线没有数据 |
   | `cls=串扰` | 读到的是时钟串扰（槽位错/线悬空） |
   | `dup≈1.0` | 采样率减半（BCLK 只有 32×fS，说明用了 16bit 槽） |

2. 核对 `CONFIG_VW_MIC_SLOT`：`L/R` 接地选左声道、接 VDD 选右声道；
   **默认 AUTO 会自动探测并在日志打印 `已自动切换到 x 声道`**。

3. 核对引脚：GPIO 号与原理图一致，且**没有被摄像头占用**（本工程不启用摄像头，
   排线建议拔掉，否则它会占用 I2S/GPIO）。

4. 供电：INMP441 要 3.3V，且 **VDD 与 GND 必须与 ESP32 共地**。共地不良时
   数据线呈静止线，时钟也看不到。

## 6. `mic peak` 恒定为 ±21845/±21846

**症状**

```
I (1204) app:voice: mic peak=21845 (state=0)
I (3204) app:voice: mic peak=21845 (state=0)
```

数值几乎不变、量级还很大（-3dBFS 左右），看起来"声音很响"，但唤醒永不触发。

**原因**：读到的是 **BCLK 时钟串扰**，不是麦克风数据。21845 = `0x5555`，
21846 = `0x5556`，是典型的 `0101` 交替图案（时钟线耦合到数据线）。

**处理**

1. 确认用了 **32bit 槽宽**（16kHz 时 BCLK 应为 1.024MHz，即 64×fS）。
2. 换槽位：`CONFIG_VW_MIC_SLOT_LEFT` ↔ `RIGHT`，或直接用 AUTO 让它探测。
3. 检查 SD（数据）线是否虚焊/接触不良——串扰通常意味着 SD 悬空，只有时钟在动。

## 7. 静止线（STUCK）

**日志**

```
W (5204) app:voice: 麦克风数据无效[静止线]：SD 线上没有数据（麦克风未驱动），请检查供电/时钟/接线
```

**判据**：一帧里几乎所有样本都是 `0xFFFF`/`0x0000`（本工程的 `stuck_ratio > 0.97`）。

**已踩过的真实案例**：`raw32=FFFFFFFF`。原因是麦克风的 **SD 线没有真正接到 GPIO**——
模块 6 个焊盘、丝印是镜像的，按箭头方向理解会接反。修正接线后恢复正常。

**处理**

- 万用表量：VDD 3.3V、GND 通、SD 与 GPIO6 之间通断正常。
- 示波器/逻辑分析仪看 BCLK 与 WS 是否有波形（BCLK 1.024MHz、WS 16kHz）。
- 模块的 `L/R` 脚必须接 GND 或 VDD，**悬空会导致输出无驱动**。

## 8. 时钟串扰（CROSSTALK）

**日志**

```
W (5204) app:voice: 麦克风数据无效[时钟串扰]：读到的是 BCLK 串扰，请检查 L/R 槽位与 SD 接线
```

**判据**：相邻样本逐点等幅反号（`alt_ratio` 高）。

**处理**：与 §6 相同——先换槽位，再查 SD 接线。

> 自检函数是 `audio_i2s_check_frame()`，返回值 `AUDIO_LINE_OK/STUCK/CROSSTALK`。
> 它把"麦克风没工作"和"真的有声音"区分开，避免被 `peak` 数值误导。

## 9. 喇叭长鸣或播完仍在响

**症状**：一段 TTS 播完后扬声器持续响，或者一直重复最后一个音节。

**原因**：`i2s_chan_config_t.auto_clear` **默认是 `false`**。没有新数据时，
TX DMA 会把上一次的缓冲区**循环重发**，听感就是长鸣/卡住的音节。

**处理**（`audio_i2s.c`）：

```c
i2s_chan_config_t chan_cfg = I2S_CHANNEL_DEFAULT_CONFIG(I2S_NUM_1, I2S_ROLE_MASTER);
chan_cfg.auto_clear = true;          // ← 必须
```

改完重新烧录即可。另外本工程已按需求**移除了开机蜂鸣测试**（`audio_i2s_boot_beep`），
如果还能听到上电"嘀"一声，说明烧的是旧固件。

## 10. 功放没声音或只响一边

先单独验证功放，用 `test/amp_test/`：

```bash
cd firmware/test/amp_test
idf.py set-target esp32s3 && idf.py -p COMx flash monitor
```

它会用 3 种帧格式轮播，靠"响几声"判断哪种格式对：

| 现象 | 结论 |
|---|---|
| 响 1 声 | 第 1 种格式可用 |
| 响 2 声 | 第 2 种可用 |
| 响 3 声 | 第 3 种可用 |
| 全程无声 | 供电/接线问题，先查 `SD_MODE` 与 `GAIN` |

**接线核对**

- `SD_MODE` 必须拉高（3.3V）才输出；悬空时芯片处于关断。
- `GAIN` 悬空 9dB / 接 GND 12dB / 接 VDD 15dB。
- MAX98357A 的 `VIN` 建议 5V（音量更大），3.3V 也能工作但声小。
- **只响一边**：本工程 TX 用 16bit 立体声并把单声道复制到 L/R 两槽，
  理论上通吃；若仍只响一边，检查喇叭是否接在正确的 `+/-` 上。

## 11. 连不上上位机

**日志特征**

```
E (3204) comm:net: connect 192.168.1.10:8888 failed: ESP_ERR_ESP_NETIF_... 
W (5204) comm:net: reconnect in 3000 ms
```

**排查**

1. **`host_ip` 填的是上位机 IP，不是设备 IP**。上位机启动日志会打印
   `本机 IP=x.x.x.x，下位机 host.ip 应填这个地址`，照抄。
2. 同一网段：设备连的 WiFi 与上位机必须在同一网段（`ipconfig` 对比前三段）。
3. 上位机端口被占：上位机日志会报 `TCP 监听 0.0.0.0:8888 失败`，换端口或关掉占用进程。
4. Windows 防火墙拦截入站 8888 —— 首次运行时允许"专用网络"访问。
5. WiFi 没连上：日志会有 `wifi disconnected reason=...`。
   此时设备会起 **AP 热点 `VoiceWake-XXXX`**，手机连上后访问配置页写入凭证。
6. 2.4GHz only：ESP32-S3 不支持 5GHz，SSID 别选 5G 频段。

## 12. 反复连接/断开

**症状**：每 2010ms 左右连一次断一次，日志交替出现 `host connected` / `host disconnected`。

**根因（两个必须同时修）**

1. 下位机把 `recv()` 超时（`SO_RCVTIMEO`，2s）返回的 `-1/EAGAIN` 当成断链处理。
2. **上位机不回心跳**：设备只发不收 → "最近接收时间"永不刷新 → 判超时 → 主动断开重连。

**修复**

- 下位机：`recv() < 0 && errno != EAGAIN` 才算断链。
- 上位机：`pipeline._reply_heartbeat()` 收到 `HEARTBEAT` 后回一帧空心跳。

**验证**：连线稳定后日志应只在真正断网时出现 `host disconnected`。

## 13. 唤醒命中但跳过会话

**日志**

```
W (8204) app:voice: 唤醒已命中，但上位机未连接，跳过本次会话
```

**说明**：这是**保护逻辑**，不是故障。未连接时开会话会让上行音频全部丢在 socket 里，
不如明确跳过。看到这条日志说明"唤醒链路是通的"，问题在网络侧 → 转 [§11](#11-连不上上位机)。

## 14. 每句话都录满 15 秒

**日志**

```
I (20000) app:voice: session 3 end (max)
```

**原因**：端点检测只依赖 AFE 的 VAD。噪声偏大或带直流偏置时 VAD 一直判"语音"，
会话就一路录到 `MAX_CAPTURE_FRAMES`(15s)，端到端延迟和 STT 负担都变差。

**修复**（fw 0.4.x 起已在代码里）：

```c
int ac_rms = frame_ac_rms(mic, FRAME_SAMPLES);          // 先减均值再算 RMS
bool voiced = (sr.vad == VW_VAD_SPEECH) || (ac_rms > SPEECH_RMS_TH);   // 300
```

并新增 `WAIT_SPEECH_FRAMES`(3s)：唤醒后一直没人说话就直接 `end("nospeech")`，
不再把 15 秒静音送去识别。

**自检**：正常一句话应在说完后 ~800ms 内出现 `session N end (vad)`。

## 15. 播报飞快

**症状**："1 秒说完了 10 秒的话"，声音像快进。

**这不是音频格式或采样率问题**（上位机侧已实测：29 字文本合成出 5.07s 音频）。
真正原因是**下发节奏**：

- 上位机把 5.07s 的音频拆成 253 帧，在几十毫秒内一次性推完；
- 下位机播放队列只有 8 帧（旧版本），`xQueueSend(..., 0)` 满即丢，
  只播了前 ~160ms，其余被静默丢弃。

**修复（两侧都要）**

| 侧 | 改动 |
|---|---|
| 上位机 | `_send_audio_frames` 按 ≈实时节奏发（每帧 20ms，领先播放 150ms） |
| 下位机 | 队列 8 → **40 帧**（≈800ms）；入队超时 0 → 10ms；丢帧时限频告警 |

验证：1.0s 音频应耗时约 0.85s 发完（50 帧），设备播放连续无缝。

## 16. 唤醒没有回复词

**时序**：设备 `session.start{need_ack:true}` → 等上位机下发"在的"音频 → 播完才采集。

**排查**

1. 设备侧 `ack_enable` 是否开启：

   ```
   grep ack_en < flash 出来的 NVS>    # 或上位机设备页「唤醒回复词」下拉框
   ```
2. 上位机 `config.json → device.ack_enable` / `device.ack_text`。
3. 上位机日志是否出现 `ack 合成失败`（TTS 模型没加载成功）。
4. 设备日志是否有 `ack timeout`——有的话说明上位机一帧都没发过来，
   但**设备仍会继续采集**（4s 兜底），功能不受影响，只是少了回复词。

> 上位机在 `ack_enable=false` 或合成失败时，会发一个**空 END 帧**，
> 让设备立刻进入采集，避免白等 4 秒。

## 17. 内存问题

**观察**

```
I (12345) main: ... free_heap=180000
```

关注点：

| 现象 | 原因 | 处理 |
|---|---|---|
| `free_heap` 逐步下降到 0 后重启 | 任务里 malloc 未 free / 队列未回收 | 复查 `cJSON_Delete`、`free()` |
| 一启动就 `free_heap` 很小 | PSRAM 没启用，AFE 挤在内部 RAM | 确认 `CONFIG_SPIRAM=y` |
| `create play queue failed` | `PLAY_QUEUE_DEPTH` 过大或内存碎片 | 减小深度 |
| `create audio task failed` | 栈 8192 太大 | 降到 6144 并复查大数组是否在栈上（`int16_t mic[320]` 只占 640B） |

`vw_err_t` 里 `0x0101 VW_ERR_NOMEM` 表示内存类失败，日志会带上具体是哪一步。
