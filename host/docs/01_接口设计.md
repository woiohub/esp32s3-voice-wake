# 上位机接口设计（Python）

> 适用版本：**host v0.7.2**
> 对应实现：`voice_assistant/protocol.py`、`network.py`、`pipeline.py`
> 下位机侧同名文档：`../../firmware/docs/01_接口设计.md`

本文是**上位机视角**的接口契约，分三块：

1. **对外**（对下位机）：帧协议、命令、音频节奏 —— 与固件字节级对齐；
2. **对内**（对 GUI）：`pipeline` 的回调事件表 —— GUI 只依赖这些回调，不碰业务逻辑；
3. **错误码**：日志页会读取本文的错误码表做解释。

---

## 1. 连接与角色

| 项 | 约定 |
|---|---|
| 角色 | 上位机是 **TCP 服务端**，`asyncio.start_server` 监听 |
| 默认监听 | `0.0.0.0:8888`（`config.json → network.host/port`） |
| 并发连接 | 只接受 1 个设备连接；新连接进来会替换旧的（`server.connection`） |
| 断线检测 | 依赖对端关闭 / 读异常；无应用层超时判死（心跳由设备侧发起） |

设备上线后第一件事是发 `hello`，上位机把它存进 `pipeline.device_info`
并通过 `on_device` 回调刷到设备页。

## 2. 帧协议（与固件字节级一致）

```python
# voice_assistant/protocol.py
HDR_LEN   = 16
CRC_LEN   = 2
MAX_FRAME = 65536

TYPE_CONTROL    = 0x01
TYPE_AUDIO_UP   = 0x02
TYPE_AUDIO_DOWN = 0x03
TYPE_HEARTBEAT  = 0x04
TYPE_ACK        = 0x05

AUDIO_FLAG_START      = 0x01
AUDIO_FLAG_END        = 0x02
AUDIO_FLAG_HAS_SPEECH = 0x04
```

| 偏移 | 字段 | 长度 | 说明 |
|---|---|---|---|
| 0 | MAGIC | 2 | `0xAA 0x55` |
| 2 | VERSION | 1 | `0x01` |
| 3 | TYPE | 1 | 见上 |
| 4 | SEQ | 4 | 大端 u32（每个方向独立递增） |
| 8 | TIMESTAMP_MS | 4 | 大端 u32，开机单调毫秒 |
| 12 | PAYLOAD_LEN | 4 | 大端 u32 |
| 16 | PAYLOAD | N | |
| 16+N | CRC16 | 2 | CCITT-FALSE（0x1021 / 0xFFFF） |

关键函数：

| 函数 | 作用 |
|---|---|
| `crc16(data) -> int` | CCITT-FALSE |
| `build_frame(type_, seq, ts_ms, payload) -> bytes` | 组帧 |
| `pack_audio(session_id, flags, pcm) -> bytes` | 音频子帧（4B sid + 1B flags + PCM） |
| `unpack_audio(payload) -> (sid, flags, pcm)` | 拆音频子帧 |
| `FrameParser.feed(data) -> list[frame]` | 流式解析，处理粘包/半包 |
| `now_ms()` | 单调毫秒（不取 Unix 纪元，避免 u32 溢出） |

> `now_ms()` 用 `time.monotonic()` 而不是 `time.time()`：
> Unix 纪元毫秒是 13 位数，塞进 u32 会截断成随机值。

## 3. 控制帧

### 3.1 上位机 → 设备（下发的命令）

| cmd | params | 用途 | GUI 触发点 |
|---|---|---|---|
| `config.get` | `{}` | 读取设备当前配置 | 设备页「读取当前配置」 |
| `config.set` | `volume, wake_enable, ack_enable` | 批量下发 | 设备页「下发配置」 |
| `volume.set` | `volume` | 单独调音量（滑杆实时） | 设备页音量滑杆 |
| `wifi.set` | `ssid, password` | 写 WiFi 凭证（设备重启生效）。**配网场景下发不出去**（设备没有 TCP），实际配网走蓝牙 | 调试用 |
| `host.set` | `ip, port` | 写上位机地址（设备重启生效） | 设备页「下发配置」 |
| `wakeword.set` | `enable` | 启停唤醒 | 设备页「唤醒开关」 |
| `status.get` | `{}` | 查状态 | 调试用 |
| `reboot` | `{}` | 重启设备 | 调试用 |
| `prov.start` | `{}` | 让设备打开蓝牙配网窗口（换 WiFi 用） | 设备页「让设备进入配网」 |

每条命令带一个 `id`（`uuid4().hex[:8]`），设备原样回传，上位机靠它匹配应答：

```python
async def request_device(self, conn, cmd, params, timeout=3.0):
    req_id = uuid.uuid4().hex[:8]
    self._pending[req_id] = cmd
    await conn.send_control({"id": req_id, "cmd": cmd, "params": params})
    # 应答到达 → _on_control 里 pop(_pending) → on_ack(cmd, code, result)
```

GUI 线程调用入口（线程安全）：

```python
pipeline.submit_device_request(conn, "config.set", params, loop)
# 内部用 asyncio.run_coroutine_threadsafe 投递到 server.loop
```

### 3.2 设备 → 上位机（收到的事件）

| cmd | 处理 |
|---|---|
| `hello` | 存 `device_info` → `on_device(info)` → 设备页刷新 |
| `session.start{need_ack}` | 若 `need_ack` → 起 `_send_ack()` 任务；否则直接 `on_stage("capture","active")` |
| `session.end{reason}` | `on_stage("capture","done")`；`reason=="interrupt"` 时触发 `on_interrupt` |
| 带 `id`+`code` 的消息 | 视为命令应答 → `on_ack(cmd, code, result)` |

**`hello` 的重发**：设备在 `config.set` / `volume.set` / `wakeword.set` 成功后会**主动补发一次
`hello`**。首次记为"设备上线"，之后的记为"设备信息已同步"（`pipeline._on_control` 里用
`_hello_seen` 区分）。设备页显示值一律以 `hello` 为准，`config.set` 的 `result` 只用于提示。

`reason` 取值：`vad`（静音判定）/ `max`（15s 上限）/ `nospeech`（唤醒后 3s 无语音）/
`interrupt`（播报中被打断）。

## 4. 音频帧与**下发节奏**

### 4.1 上行（收）

- 按 `session_id` 累积到 `Session.chunks`，收到 `END` 后起 `_process()` 任务。
- 同时每 2 帧算一次去直流 RMS 推给 `on_level`（约 25fps），供 UI 电平表。

### 4.2 下行（发）—— 必须实时节奏

```python
# pipeline._send_audio_frames
sent_ms = 0.0
lead_s = 0.15          # 允许领先播放进度 150ms，吸收网络抖动
for chunk in chunks(20ms):
    await conn.send_audio(session_id, flags, chunk)
    sent_ms += len(chunk) / 2.0 / rate * 1000.0
    delay = (t0 + sent_ms / 1000.0 - lead_s) - loop.time()
    if delay > 0:
        await asyncio.sleep(delay)
```

**为什么必须这样**：设备播放队列只有 40 帧（≈800ms），一次灌入整段 TTS 会因
队列满而丢帧，听感是"10 秒的话 1 秒念完"。实测 1.0s 音频应按 ≈0.85s 发完（50 帧）。

参数速查：

| 项 | 值 |
|---|---|
| 帧长 | 20ms = 320 样本 = 640 字节 |
| 采样率 | 16000 Hz（`config.audio.sample_rate`） |
| 领先量 | 150ms（`lead_s`） |
| 首帧 | `START` |
| 末帧 | `END`（`START|END` 同时置位当只有一帧时） |

## 5. 唤醒回复词（need_ack）时序

```
设备 ── session.start{need_ack:true} ──► pipeline
                                          │ asyncio.create_task(_send_ack)
                                          ├─ 合成 cfg.device.ack_text
                                          ├─ _send_audio_frames()（实时节奏）
                                          └─ on_stage("capture","active")
设备 ◄── AUDIO_DOWN(sid, START..END) ──────┘
      播完 → 切 APP_CAPTURE → 开始上行
```

失败/未启用时的兜底（**关键**，否则设备白等 4 秒）：

```python
await _skip(reason)      # 发一个空 END 帧（无 PCM）
await conn.send_audio(session_id, protocol.AUDIO_FLAG_END, b"")
```

触发 `_skip` 的条件：`ack_enable=false`、`ack_text` 为空、TTS 返回空、合成/下发抛异常。

## 6. 蓝牙配网（BLE Provisioning）

设备连不上路由器时开 BLE 广播，上位机用蓝牙把凭证写进去。为什么不用原来的 AP 热点：
设备开热点时**没有 TCP 连接**，`wifi.set` 根本发不出去（原方案实际失效）；
BLE 是点对点链路，不依赖 IP。

### 6.1 GATT 契约（`voice_assistant/provision.py` ↔ 固件 `vw_prov/ble_prov.c`）

| 项 | UUID | 内容 |
|---|---|---|
| Service | `a0e0f000-1e4d-4f8a-9b6c-1d2e3f4a5b60` | |
| CFG（写） | `a0e0f001-1e4d-4f8a-9b6c-1d2e3f4a5b60` | `{"ssid","password","host_ip","host_port"}` |
| STATE（读/通知） | `a0e0f002-1e4d-4f8a-9b6c-1d2e3f4a5b60` | `{"state","error","ip","fw","mac"}` |

广播名 `VoiceWake-XXXX`（XXXX = WiFi MAC 后三字节，与 `hello.mac` 对得上）。

### 6.2 状态流转

```
idle ──写入 CFG──► connecting ──拿到 IP──► ok   （设备关蓝牙 → 重启 → TCP 上线）
                       └──失败/超时──► fail  （蓝牙保持，可改密码重试）
```

### 6.3 上位机接口（provision.py，同步阻塞，供线程池调用）

| 函数 | 说明 |
|---|---|
| `available() -> (bool, str)` | 检查 bleak 与系统蓝牙；不可用时界面禁用按钮并给出原因 |
| `scan(timeout=6.0) -> [{name,address,rssi}]` | 只返回名称以 `VoiceWake` 开头的设备，按信号排序 |
| `provision(address, ssid, password, host_ip, host_port, timeout=35, report=None)` | 连接 → 写 CFG → 订阅 STATE → 等回执；返回 `{"state","error","ip"}` |
| `local_ip() -> str` | 本机局域网 IP，给「上位机 IP」输入框做默认值 |

线程模型：这些函数内部各自 `asyncio.run()`，与 GUI/网络线程互不干扰；
进度通过 `report` 回调写入线程安全队列，由页面定时器读取（见 `device_page._tick`）。

## 7. 对 GUI 的接口（回调事件表）

`pipeline` 不依赖 Qt：所有 UI 更新都通过**可选回调**完成（为 `None` 时静默跳过）。
GUI 侧由 `gui/bridge.py` 把这些回调转成 Qt Signal，再经 `QueuedConnection` 回主线程。

| 回调 | 签名 | 触发时机 |
|---|---|---|
| `on_stage` | `(stage, state, ms=0)` | 每个阶段的状态变化 |
| `on_transcript` | `(text, conf)` | STT 出结果 |
| `on_reply` | `(text)` | LLM 出回复 |
| `on_tts` | `("start" \| "done")` | 下行音频开始/结束 |
| `on_interrupt` | `()` | 播报被打断 |
| `on_level` | `(0..1)` | 上行电平（约 25fps） |
| `on_error` | `(code, msg)` | 任一步骤失败 |
| `on_device` | `(info: dict)` | 收到 `hello` |
| `on_ack` | `(cmd, code, result)` | 收到命令应答 |
| `on_status` | `(text)` | 人类可读的进度文字 |

### 7.1 `stage` 取值

`wake` / `capture` / `stt` / `llm` / `tts` / `play`

### 7.2 `state` 取值

`active` / `done` / `failed` / `skipped`

- `skipped` 用在同一阶段被跳过时：例如文本调试（`ask_text`）会跳过 `wake`/`capture`/`stt`。
- `failed` 只标记**当前**阶段，其余阶段保持原状，阶段条不会全红。

### 7.3 `ms` 语义

只在 `state="done"` 时有意义（该阶段耗时毫秒）。`on_stage` 的 `ms` 为 0 时不推时长。

### 7.4 典型序列（一句话完整流程）

```
on_stage("wake","done")
on_stage("capture","active")            ← need_ack=false 时
on_stage("capture","done")
on_stage("stt","active")
on_transcript("今天天气怎么样", 0.93)
on_stage("stt","done", 312.0)
on_stage("llm","active")
on_reply("今天晴，20 到 28 度。")
on_stage("llm","done", 640.0)
on_stage("tts","active")
on_tts("start")
on_stage("tts","done", 1450.0)
on_stage("play","active")
on_stage("play","done", 2750.0)
on_tts("done")
```

## 8. 文本调试入口（绕过唤醒与 STT）

| 方法 | 用途 | GUI 触发 |
|---|---|---|
| `ask_text(text, conn)` | LLM → TTS → 下发 | 会话页文本输入框回车 |
| `speak_text(text, conn)` | TTS → 下发（不经过 LLM） | 气泡「重新播报」、模型页「试听」 |

两者都会先发 `on_stage("wake"/"capture"/"stt", "skipped")`，让阶段条如实反映跳过的环节。
文本入口的 `session_id` 由 `_next_text_sid()` 从 1000 起递增，与设备的 session 不会撞。

## 9. 错误码

协议层（设备应答里的 `code`，日志页会解析本表）：

| code | 含义 |
|---|---|
| 0 | 成功 |
| 1001 | 帧头/魔数错误 |
| 1002 | CRC 校验失败 |
| 2001 | 未知命令 |
| 2002 | 参数非法 |
| 3001 | WiFi 未连接 |
| 3002 | 未连接上位机 |
| 4001 | 音频繁忙（正在播放/采集） |
| 5001 | 内部错误 |

上位机内部异常统一走 `on_error(0, "步骤 失败：原因")`，`code` 固定 0，
`原因` 取异常消息首行（避免弹窗里出现整段堆栈）。日志里仍有完整 `traceback`。

典型失败文案：

| 场景 | `on_error` 文案 |
|---|---|
| 模型没放 | `STT（语音识别） 失败：找不到模型文件：...（可点「一键下载模型」）` |
| Key 未填 | `LLM（大模型） 失败：未配置 api_key` |
| Key 无效 | `LLM（大模型） 失败：鉴权失败（401），请检查 api_key` |
| 设备断开 | 走 `on_device(connected=false)`，不产生 `on_error` |

## 10. 与固件的兼容性

| 变更 | 兼容策略 |
|---|---|
| 设备 `hello` 新增字段（`mac/rssi/wakeword/volume`） | 老固件不发 → 设备页显示 `—`，不报错 |
| 设备不支持 `need_ack` | 上位机只在收到 `need_ack=true` 时才发回复词；老固件不发该字段 → 走普通流程 |
| 设备不支持 `ack_enable`（`config.set` 忽略该键） | 设备侧行为不变，上位机不校验 |
| 音频参数不一致 | **不兼容**，必须两侧同时改 `sample_rate` / `frame_ms` |
| 协议版本 `VERSION` | 当前 `0x01`，解析时不强校验（只用于日志），升级需同步改两侧 |
