## 1. `ModuleNotFoundError: No module named 'PySide6'`

**原因**：用了没装依赖的解释器。常见于装了多个 Python（系统 Python、Anaconda base、
项目 venv、conda env）却直接敲 `python main.py`。

**处理**

```bash
# 1) 确认当前用的是哪个 python
python -c "import sys; print(sys.executable)"

# 2) 方式 A：项目虚拟环境
cd host
python -m venv .venv
.venv\Scripts\activate            # Windows
pip install -r requirements.txt

# 3) 方式 B：conda 环境
conda create -n voice-upper python=3.10 -y
conda activate voice-upper
pip install -r requirements.txt

# 4) 验证
python -c "import PySide6, faster_whisper, piper; print(PySide6.__version__)"
```

> 项目里没提供 `.venv`，每个环境都要单独 `pip install`。
> 每次开新终端都要先激活环境，否则又会回到系统 Python。

## 2. `NameError` / `ModuleNotFoundError` 指向自己写的模块

**典型**

```
Traceback (most recent call last):
  ...
NameError: name 'asyncio' is not defined
```

**原因**：模块被引用但没 import。`main.py` 里调用了 `main_window.run_gui()`，
而 `run_gui` 内部用到 `asyncio.new_event_loop()` 却没在文件顶部 `import asyncio`，
运行到那一行才炸——这种错误用 `python -c "import ..."` 是发现不了的。

**定位手法**

```bash
cd host
python -m compileall -q voice_assistant       # 只查语法
python -m pyflakes voice_assistant            # 查未定义名/未使用 import（推荐）
```

**处理**：补 import。修完再跑一次上面的命令，确认零输出。

## 3. 端口被占用

**日志**

```
ERROR: TCP 监听 0.0.0.0:8888 失败：[Errno 10048] error while attempting to bind on
address ('0.0.0.0', 8888): 通常每个套接字地址(协议/网络地址/端口)只允许使用一次。
```

**原因**：上一次的 `python main.py` 没关干净（窗口关了但进程还在），或别的软件占了 8888。

**查**

```powershell
Get-NetTCPConnection -LocalPort 8888 -State Listen | Select-Object OwningProcess
Get-Process -Id <上面的PID> | Select-Object Id, ProcessName, StartTime
```

**处理**

```powershell
taskkill /PID <PID> /F
```

或者改端口（两侧都要改）：

- `host/config.json → network.port`
- 下位机 `idf.py menuconfig → Voice Wake System → 上位机 TCP 监听端口`

> 只改一侧 = 永远连不上。

## 4. 设备连不上

上位机侧确认顺序：

1. **监听地址**：`0.0.0.0`（不是 `127.0.0.1`）。`127.0.0.1` 只接受本机连接。
2. **启动日志里的本机 IP**：

   ```
   INFO: 本机 IP=172.17.253.195，下位机 host.ip 应填这个地址（当前配置 host_ip=）
   ```

   把这行 IP 填到设备页「上位机 IP」并下发，或写进设备 `menuconfig` 的默认上位机 IP。
3. **防火墙**：Windows 首次运行会弹窗，选「专用网络」允许。已误点拒绝的话：

   ```powershell
   # 以管理员身份运行
   New-NetFirewallRule -DisplayName "VoiceAssistant 8888" -Direction Inbound `
       -Protocol TCP -LocalPort 8888 -Action Allow
   ```

4. **同网段**：`ipconfig` 对比 PC 与设备拿到的 IP 前三段是否一致。
5. **设备确实连上了吗**：正常应有

   ```
   INFO: tcp server listening on 0.0.0.0:8888
   INFO: device connected: ('172.17.253.46', 59597)
   INFO: 设备上线: {"device": "esp32s3", "fw": "0.5.0", "audio": {...}}
   ```

   有 `device connected` 但没有 `设备上线` → 设备 `hello` 没发出来，问题在固件侧。

## 5. 反复连接/断开

**日志**：`device connected` / `device disconnected` 每 2 秒交替。

**根因**：设备把 `recv()` 超时（`SO_RCVTIMEO=2s`）当成断链；而**上位机不回心跳**——
设备只发不收，"最近接收时间"永不刷新，于是判超时主动重连。

**修复**（fw/host 双侧，本仓库均已修）：

| 侧 | 改动 |
|---|---|
| 固件 | `recv()<0 && errno != EAGAIN` 才算断链 |
| 上位机 | `pipeline._reply_heartbeat()` 收到 `HEARTBEAT` 后回一帧空心跳 |

**验证**：连线稳定后，只有真正断网才会出现 `disconnected`。

## 6. STT 未就绪

**日志**

```
WARNING: 【STT 未就绪】找不到模型文件：E:\...\models\whisper\faster-whisper-small
         缺少：model.bin, tokenizer.json（可点「一键下载模型」）
```

**原因**：`stt.model_dir` 指到了错误的层级。faster-whisper 要求目录里**直接**有
`model.bin` / `config.json` / `tokenizer.json`。

**核对**

```bash
cd host
ls models/whisper                       # 应看到 faster-whisper-small/
ls models/whisper/faster-whisper-small  # 应看到 model.bin config.json tokenizer.json ...
```

如果多套了一层（`faster-whisper-small/faster-whisper-small/model.bin`），
把 `stt.model_dir` 改到**含 `model.bin` 的那一层**。

**三种补救**

1. 界面「模型」页 → 点「一键下载模型」（会弹窗告知体积）；
2. 勾选「允许程序自动下载」后重启（`stt.auto_download=true`）；
3. 手动下载后把 `stt.model_dir` 指过去（**默认行为，推荐**）。

## 7. 模型下载超时（`WinError 10060`）

**日志**

```
urllib3.exceptions.ConnectTimeoutError: ...
OSError: [WinError 10060] 由于连接方在一段时间后没有正确答复或连接的主机没有反应
```

**原因**：直连 `huggingface.co` 在国内不通。

**处理**：确认 `config.json` 里

```json
"stt": { "hf_endpoint": "https://hf-mirror.com" }
```

代码在 **import faster_whisper 之前**把它写进 `HF_ENDPOINT`，所以改配置就够，不用改代码。

仍不通时：用浏览器/迅雷手动下载 `Systran/faster-whisper-<size>` 的
`model.bin` / `config.json` / `tokenizer.json` / `vocabulary.txt`，放好后指定 `model_dir`。

## 8. 模型下载 `os error 5`

**日志**

```
I/O error (os error 5): 拒绝访问。 (os error 5)
  ... .cache\huggingface\xet\logs\...
```

**原因**：HuggingFace 的 **xet 后端**往用户目录 `C:\Users\<user>\.cache` 写传输日志，
被安全软件/权限设置拦下。注意这跟模型目录权限无关，改权限也没用。

**处理**（`stt.py` 已做，确认这两项生效即可）：

```python
os.environ.setdefault("HF_HUB_DISABLE_XET", "1")     # 关掉 xet 后端
os.environ.setdefault("HF_HOME", "models/hf_home")   # 缓存放项目内
```

> `HF_HOME` 必须在 import 时设置，运行时再改无效。

## 9. LLM 未就绪

**日志**

```
WARNING: 【LLM 未就绪】未配置 api_key：请填写 config.json → llm.api_key，或在界面「模型」页填写
```

或会话时报：

```
LLM（大模型） 失败：鉴权失败（401），请检查 api_key 是否正确、是否已过期
```

**处理**

| 现象 | 原因 | 处理 |
|---|---|---|
| `未配置 api_key` | `llm.api_key` 为空 | 模型页填写并保存，或直接改 `config.json` |
| 401 / 403 | key 错、过期、无该模型权限 | 控制台核对 key；确认 `llm.model` 与账号开通的模型一致 |
| 429 | 限流/额度用尽 | 换 `glm-4-flash`（免费额度）或稍后再试 |
| 超时 | 网络或 `llm.timeout` 太小 | 默认 30s；代理环境要确认代理对 SDK 生效 |
| `连接失败` | `base_url` 与 `provider` 不匹配 | GLM 用 `.../api/paas/v4`；Qwen 用 `.../compatible-mode/v1` |

**最快验证**：模型页点 **「测试大模型」**（`F5`），它会直接发一条最短请求并把
原始错误显示在按钮右侧。

## 10. TTS 未就绪

**日志**

```
WARNING: 【TTS 未就绪】模型文件不存在：...\models\piper\zh_CN-huayan-medium.onnx
```

Piper 需要**两个**文件放同一目录：

```

```

`config.json → tts.model_path` 要指到 `.onnx` 文件本身（不是目录）。

## 11. "处理失败"怎么定位

v0.7.0 起失败文案会带步骤名（不再是一句笼统的"处理失败"）：

```
STT（语音识别） 失败：找不到模型文件：...
LLM（大模型） 失败：鉴权失败（401）...
TTS（语音合成） 失败：Piper 合成返回空音频
下行音频发送 失败：Connection lost
```

排查顺序：

1. 看**步骤名**确定环节；
2. 看日志页（`Ctrl+4`），`ERROR` 行有染色，双击可看错误码说明；
3. 完整堆栈在 `logs/` 目录的滚动日志文件里。

## 12. 播报飞快

**症状**：一句话"瞬间念完"，像快进。

**先证伪**：TTS 本身没问题。实测 29 字文本合成出 **5.07s** 音频（16k）。

**真正原因**：下发节奏。5.07s 音频 = 253 帧，若在几十毫秒内一次性推给设备，
设备播放队列（旧版 8 帧）会满，`xQueueSend(...,0)` 直接丢弃，只播了前 ~160ms。

**修复（两侧）**

| 侧 | 改动 |
|---|---|
| 上位机 | `_send_audio_frames` 按实时节奏发：每帧 20ms，领先播放 150ms，用 `asyncio.sleep` 补差 |
| 固件 | 队列 8 → 40 帧（≈800ms），入队超时 0 → 10ms，丢帧限频告警 |

**自检**：日志里应有

```
已下发回复音频 5.0s
```

且下发**耗时**接近音频时长（而不是几毫秒）。

## 13. 播报变调（音调偏高）

**症状**：语速和音调都高了约 1.38 倍（22050/16000）。

**原因**：Piper 模型输出 22050Hz，链路要 16000Hz，**没做重采样**就丢给了设备。

**处理**：`tts.py` 已内置 `resample_int16()`（numpy 抗混叠低通 + 线性插值），
启动日志会打印：

```
INFO: Piper 输出 22050 Hz，将重采样到 16000 Hz
```

没有这行 → 跑的是旧代码。

## 14. 唤醒没有回复词

**期望行为**：设备 `session.start{need_ack:true}` → 上位机立刻合成 `device.ack_text` 下发 →
设备播完才开始采集。

**排查**

| 检查 | 位置 |
|---|---|
| 回复词开关 | 设备页「唤醒回复词」下拉；`config.json → device.ack_enable` |
| 回复词文本 | 设备页「回复词文本」；`config.json → device.ack_text` |
| 上位机日志 | 应有 `唤醒回复词：在的（合成 XXXms，0.6s 音频）` |
| TTS 是否就绪 | 若 TTS 未就绪会走 `_skip`，日志 `ack skipped: ...` |

> `_skip` 时会发一个**空 END 帧**，设备立即进入采集——
> 所以"没有回复词但功能正常"通常就是 TTS 没就绪或开关关了。

## 15. 界面白色方块与控件被压扁

深色主题下出现白色块，几乎都是**没被 QSS 覆盖的原生子控件**：

| 现象 | 原因 | 修法 |
|---|---|---|
| 按钮是白底方块 | `QToolButton` 没写全局规则、`objectName` 为空 → 走系统原生样式 | 加 `QToolButton { background: transparent; }` |
| 右侧一条浅色竖条 | 滚动条只写了 `::handle`，没写 `::add-page/sub-page` | 补 `background: transparent` |
| 复选框是浅色方框 | 没写 `QCheckBox::indicator` | 自定义 indicator；勾选态的对勾用 `icons` 渲染 PNG 再 `image: url()` |
| 数字框只看得到箭头 | `setFixedWidth(64)` 小于 QSS 下的 `sizeHint`(94) | 按 `sizeHint` 定宽（`device_page._fit_spin`） |
| 下拉框/输入框被压成细条 | 垂直空间不足，Qt 把控件压到低于 `sizeHint` | 外套 `QScrollArea` + QSS `min-height` |

**自查命令**（不用开窗口就能看几何）：

```python
c = page.volume_spin
print(c.width(), c.sizeHint().width())   # 前者必须 ≥ 后者，否则一定被裁
```

> 反过来，**不要用 QSS 接管 `QSpinBox::up-button/down-button`**：
> 一旦写了，Qt 就不再绘制原生箭头，而 border 三角在 QSpinBox 上不生效。

## 16. 界面卡死

**症状**：窗口白屏/转圈，点按钮没反应。

**原因**：在 UI 线程里做了阻塞调用。最常见的三个：

| 操作 | 阻塞时长 | 正确做法 |
|---|---|---|
| 首次加载 STT 模型 | ~1.3s | `tasks.run_task(stt.preload, ...)` |
| 首次加载 Piper 模型 | ~3.6s | 同上 |
| 试听/测试大模型 | 1~3s | 同上 |

**自查**：搜索 `gui/` 目录里有没有直接调 `self.stt.` / `self.llm.` / `self.tts.` 的同步方法，
或 `time.sleep`。规范写法：

```python
from ..tasks import run_task
run_task(self.stt.preload, self._on_preload_done, tag="stt")
```

## 18. 蓝牙配网问题

**前提**：配网**不依赖网络**，只依赖本机蓝牙。设备处于配网态时会广播 `VoiceWake-XXXX`。

### 18.1 「扫描」按钮是灰的

启动时界面调 `provision.available()` 做了检查，失败原因会显示在按钮右侧：

| 提示 | 处理 |
|---|---|
| `未安装 bleak：pip install bleak` | `pip install bleak`（或重装 `requirements.txt`） |
| Windows 报蓝牙不可用 | 设置 → 蓝牙和其他设备 → 打开蓝牙；台式机需要蓝牙适配器 |

### 18.2 扫不到设备

排查顺序：

1. **设备真的在配网态吗**——串口日志应有
   `W (xxxx) srv:prov: 进入蓝牙配网：广播 VoiceWake-XXXX`；
   设备日志出现这条的时机：NVS 无凭证上电，或 WiFi 连续失败 5 次，
   或你在设备页点过「让设备进入配网」。
2. **配网窗口超时了吗**——默认 300 秒没人连接就退出并回 WiFi 重连，重新触发即可。
3. **蓝牙适配器会不会只支持经典蓝牙**——个别 USB 适配器不支持 BLE，换个原生的。
4. **离设备太远**——BLE 广播距离有限，先放近一点。

### 18.3 能连上但写入失败

| 现象 | 原因 | 处理 |
|---|---|---|
| `等待设备回执超时` | 设备端配网任务被占死或版本太旧 | 重启设备再试；确认固件 ≥ 0.6.0 |
| `cannot join WiFi (password or signal)` | 密码错 / 信号弱 / 5GHz | **蓝牙还开着**，直接改密码再点一次「写入设备并连接」 |
| `ssid required` / `bad json` | 写入内容不完整 | 检查 SSID 是否为空 |
| 写入时立刻断开 | 设备已连上 WiFi 并在重启 | 正常现象，等 TCP 上线即可 |

### 18.4 配网成功但设备没连上上位机

配网成功后设备会**重启**（让新的上位机 IP/端口生效），重启后走正常 TCP 连接。
没连上就按 [§4](#4-设备连不上) 排查——最常见是「上位机 IP」填错，
注意这里填的是**配网卡里的那一份**，不是参数卡里的。

### 18.5 一句话

> 配网链路（蓝牙）与语音链路（WiFi/TCP）是两条独立的路；配网只负责把凭证写进 NVS，
> 之后设备重启、连 WiFi、连 TCP、发 `hello`，走的是和正常开机完全一样的流程。
